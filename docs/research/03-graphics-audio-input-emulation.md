# 03 — Graphics, audio, input and windowing: the minimum faithful surface, and the backend strategy

RetroBug research track: **the 32-bit guest system-library layer above the emulated CPU**. Scope: what
`armeabi-v7a` apps actually link, what a modern 64-bit host still provides, which parts must be
reproduced in 32-bit guest form, and one backend strategy that survives both Android and iOS.

Process architecture is taken as given from doc 02: guest DEX runs on host 64-bit ART; only
`lib/armeabi-v7a/*.so` is emulated. RetroBug therefore ships **32-bit guest versions of Android's
native system libraries whose functions accept ARM32 calls and forward into the host's real
64-bit graphics/audio/input stacks.**

**Method / how to re-verify.** AOSP files were read from
`https://android.googlesource.com/<repo>/+/refs/heads/main/<path>?format=TEXT` (base64 body) and
upstream project files from `raw.githubusercontent.com`/the GitHub API; line numbers are real
file lines on `refs/heads/main` (or `master`) as of 2026-09 unless a tag is named. CDD statements are
cited by **requirement tag** (`[C-1-1]`) rather than line number, because those are stable. Claims
that are not from a primary source are marked **inference** or **unverified**.

**The single biggest reuse opportunity:** AOSP already contains a generated 32-bit-ARM build of
exactly the proxy/guest shim libraries RetroBug needs —
[`frameworks/libs/native_bridge_support/android_api/`](https://android.googlesource.com/platform/frameworks/libs/native_bridge_support/+/refs/heads/main/android_api/)
containing `libEGL`, `libGLESv1_CM`, `libGLESv2`, `libGLESv3`, `libOpenSLES`, `libOpenMAXAL`,
`libaaudio`, `libamidi`, `libandroid`, `libandroid_runtime`, `libnativewindow`, `libvulkan`,
`libjnigraphics`, `libmediandk`, `libc`, `libcamera2ndk`, `libbinder_ndk`, `libnativehelper`,
`libneuralnetworks`, `libwebviewchromium_plat_support`, plus `linker` and `vdso` — each with a
`arch: { arm: { srcs: ["stubs_arm.cc"] } }` variant, `stem:` set to the real library name and
`overrides:` set to the real module name, generated by `gen_proxy_libraries.py`. **RetroBug does not
hand-write guest stubs.** It runs/reuses that generator. See §1.6.

**Biggest correctness risk:** GLES 1.x fixed-function fidelity (§2). Quantified: ANGLE gates its
generated shaders on a **13-bit** `GLES1StateEnables` mask → up to 8192 shader variants per texture-unit
configuration, plus per-context caps (matrix stack depth, light count, unit count, combiner inputs)
and semantics with *no* modern hardware analogue (two-sided lighting, point sprites, line smoothing,
logic-op-via-framebuffer-fetch). Mitigation and the oracle idea are in §7.

**Backend recommendation (one paragraph, decisive):** Forward, don't translate, on Android; translate
once, on iOS, with ANGLE. RetroBug's guest GL layer is a proxy `libEGL`/`libGLESv1_CM`/`libGLESv2`/
`libGLESv3`/`libvulkan` that forwards to the **host's native driver by default** (the CDD guarantees
GLES 1.1–3.1 exists there), with **ANGLE as a per-app drop-in replacement host backend** — reusing
`libEGL_angle`/`libGLESv1_CM_angle`/`libGLESv2_angle` exactly as Android itself uses them to rescue
apps from bad or missing driver paths — and **SwANGLE (ANGLE→SwiftShader) as the deterministic CPU
reference renderer** for golden-image testing. On iOS, where GL is a deprecated dead end and absent
altogether on visionOS, RetroBug keeps the *same* guest API surface and re-targets ANGLE's existing
`renderer/metal` backend (`driver_utils_ios.mm`), while guest **Vulkan** is forwarded to MoltenVK with
`VK_KHR_portability_enumeration` forced on RetroBug's side. Do **not** make Vulkan the single host
backend on Android: it adds a GLES→Vulkan translation in front of a driver that already implements
GLES natively, and it inherits MoltenVK's portability-subset caveats on devices that don't need them.
Full reasoning and the counter-argument: §6.

## 1. The 32-bit-era graphics API surface

### 1.1 What is actually mandatory — the authoritative list

The Android 16 CDD's required shared-library enumeration is the closest thing to a specification for
RetroBug's guest layer. Verbatim entries (§7.1, "MUST" shared library list):

```
libandroid.so (native Android activity support)
libamidi.so (native MIDI support, if feature android.software.midi is claimed …)
libEGL.so (native OpenGL surface management)
libGLESv1_CM.so (OpenGL ES 1.x)
libGLESv2.so (OpenGL ES 2.0)
libGLESv3.so (OpenGL ES 3.x)
libjnigraphics.so
libmediandk.so (native media APIs support)
libOpenMAXAL.so (OpenMAX AL 1.0.1 support)
libOpenSLES.so (OpenSL ES 1.0.1 audio support)
libvulkan.so (Vulkan)
```
([source](https://source.android.com/docs/compatibility/16/android-16-cdd))

Version mandates and EGL obligations from the same document:

- `[C-0-1]` MUST correctly identify supported GLES versions **(1.1, 2.0, 3.0, 3.1, 3.2)**.
- `[C-1-1]` (if it has a screen) MUST support **OpenGL ES 1.1, 2.0, 3.0, and 3.1**; SHOULD support 3.2.
- `[C-2-2]` MUST support `EGL_KHR_image`, `EGL_KHR_image_base`, `EGL_ANDROID_image_native_buffer`,
  `EGL_ANDROID_get_native_client_buffer`, `EGL_KHR_wait_sync`, `EGL_KHR_get_all_proc_addresses`,
  `EGL_ANDROID_presentation_time`, `EGL_KHR_swap_buffers_with_damage`, `EGL_ANDROID_recordable`,
  `EGL_ANDROID_GLES_layers`.
- `[C-3-1]` GLES 3.0/3.1/3.2 symbols MUST be exported from `libGLESv3.so` *in addition to* the 2.0
  symbols in `libGLESv2.so` (i.e. apps that link `-lGLESv2` still see 2.0-only symbols).
- Vulkan is **conditional**: `[C-SR-1]`/`[C-SR-2]` only *STRONGLY RECOMMENDED* (Vulkan 1.3). `[7.1.4.2/H-2-1]`
  MUST support Vulkan 1.1 *if* Vulkan is supported. **Do not assume Vulkan exists on every host; do
  assume GLES 1.1 does.**

**Consequence for RetroBug:** on Android, "forward to the host driver" is a *legally guaranteed* option
for EGL + GLES 1.1 + 2.0 + 3.0 + 3.1, and only a *best-effort* option for 3.2 and Vulkan.

### 1.2 Vendor and mythical libraries — what apps do **not** link

The brief asks about `libGLES_mali.so`, `libPowerVR`, `libGLES_mesa`. AOSP's driver-loading rules
([Implement OpenGL ES and EGL](https://source.android.com/docs/core/graphics/implement-opengl-es))
make the naming scheme explicit — these are **vendor driver blobs under `/vendor/lib{,64}/egl`**,
resolved by the EGL loader via `ro.hardware.egl` / `ro.board.platform`:

```
libGLES_${ro.hardware.egl}.so      libGLES_${ro.board.platform}.so      libGLES.so
libEGL_${ro.hardware.egl}.so       libGLESv1_CM_${ro.hardware.egl}.so   libGLESv2_${ro.hardware.egl}.so
libEGL_${ro.board.platform}.so     libGLESv1_CM_${ro.board.platform}.so libGLESv2_${ro.board.platform}.so
libEGL.so  libGLESv1_CM.so  libGLESv2.so
```

So `libGLESv1_CM_mali.so` (or a blob named `libGLES_mali.so`) is a *driver implementation of*
`libGLESv1_CM.so`, not something an APK's `lib/armeabi-v7a/` contains. **RetroBug must not try to
provide these**; guest code that `dlopen`s a vendor name directly is a bug in that code and should be
diagnosed, not chased. Likewise `libGLES_mesa` is the *Android emulator / gfxstream host* GL path, not
a device library — irrelevant as a target, though `swiftshader`/mesa matter as *reference renderers*
(§1.5).

Two real-world exceptions worth handling:
- Some 32-bit-era apps `dlopen("libGLESv2.so")` at runtime to feature-probe. Because the guest proxy
  `libGLESv2.so` is a real `dlopen`-able object in the guest namespace, this works for free.
- `libandroid_runtime` is a **private** platform library — but it is exactly what an app's native
  `dispatchTouchEvent` implementation touches, and native_bridge_support already has a guest proxy for
  it. See §5.2.

### 1.3 GLES 1.x on modern Android hosts: available, and with a documented escape hatch

Because `[C-1-1]` makes GLES 1.1 mandatory, a modern arm64 Android host has a 64-bit
`libGLESv1_CM.so`. RetroBug's guest `libGLESv1_CM.so` proxy therefore forwards to a real driver in the
general case. The residual risk is not *absence* but **quality** (old fixed-function paths on new
TBDR hardware are exactly where driver bugs live — the same class of bug doc 08 documents for
Adreno GMEM/MSAA).

Google's supported escape hatch is ANGLE as an installable, per-package-selectable GLES driver. AOSP's
Mainline ANGLE module builds exactly these libraries
([`packages/modules/ANGLE/Android.bp`](https://android.googlesource.com/platform/packages/modules/ANGLE/+/refs/heads/main/Android.bp)):

```
name: "libfeature_support_angle"   name: "libEGL_angle"
name: "libGLESv1_CM_angle"          name: "libGLESv2_angle"
name: "AospANGLE"                   name: "GoogleANGLE"
```

and the module's own Readme documents the selection surface RetroBug can copy or reuse:
`ro.gfx.angle.supported`; `settings put global angle_gl_driver_selection_pkgs <pkg>` +
`angle_gl_driver_selection_values <angle|native|default>`; `angle_gl_driver_all_angle`; and a JSON
"rules file" (`a4a_rules.json`, matched on device / GPU / Vulkan-driver version) with a
`debug.angle.rules` override. **This is a per-app GL-backend selection mechanism, already designed,
already shippable** — RetroBug's "App Revival" per-app backend flag (doc 08 §Compat-lesson 5) should
reuse its shape verbatim rather than invent one. Note the Readme's own warning that forcing ANGLE for
*all* packages currently makes the device unbootable — i.e. even Google's default path is not
universal, which is an argument for per-app opt-in rather than "ANGLE always".

### 1.4 GLES on iOS: deprecated, not removed — but a dead end

Apple's own documentation metadata for the `OpenGLES` framework (fetched as structured data from
`developer.apple.com/tutorials/data/documentation/opengles.json`, © 2026) reports:

| Platform | Introduced | Deprecated |
|---|---|---|
| iOS | 2.0 | **12.0** |
| iPadOS | 2.0 | **12.0** |
| Mac Catalyst | 2.0 | — |
| tvOS | 9.0 | 12.0 |
| **visionOS** | 1.0 | **1.0** (i.e. never available) |

Apple's retired programming guide states it plainly: *"**Important:** OpenGL ES was deprecated in
iOS 12. To create high-performance code on GPUs, use the Metal framework instead."*
([Adopting OpenGL ES 3.0](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/OpenGLES_ProgrammingGuide/AdoptingOpenGLES3/AdoptingOpenGLES3.html)).
`EAGLRenderingAPI` **still exposes `openGLES1` ("Context supports OpenGL ES 1.x rendering API")** in
the current docs ([EAGLRenderingAPI](https://developer.apple.com/documentation/opengles/eaglrenderingapi)),
so the brief's "removed in iOS 17" is **false**: GL was deprecated, not deleted, and is still
documented in 2026.

**Correction to that reading, and the reason it does not change the plan:** symbol presence ≠ context
usability on current silicon. Whether an ES 1.x context can actually be created on A7-and-later
(64-bit-only) Apple GPUs could **not** be confirmed from a primary source; widely-reported community
answers say ES 1.x is unavailable there (**unverified**, §Open questions). RetroBug must not design
around it: on iOS the plan is ANGLE→Metal regardless, which makes the question moot. Also note
**visionOS has no GL at all**, so a GL-native iOS/visionOS backend is not portable even inside Apple's
own lineup.

**Version ceiling** (what an iOS GLES backend could at most reach): Apple tops out at GLES 3.0/3.2
class support depending on GPU family; **not pinned to a primary source here** — treat as
**unverified** and, again, moot under the recommended strategy.

### 1.6 The guest stubs are already generated — `native_bridge_support/android_api`

Confirmed, in detail. `android_api/libGLESv1_CM/` contains:

```
Android.bp
proxy/gles_trampolines.cc
stubs_arm.cc      stubs_arm64.cc      stubs_riscv64.cc
```

and its `Android.bp` ([link](https://android.googlesource.com/platform/frameworks/libs/native_bridge_support/+/refs/heads/main/android_api/libGLESv1_CM/Android.bp)) is exactly the pattern RetroBug needs, verbatim (Apache-2.0, `default_applicable_licenses: ["Android-Apache-2.0"]`):

```
cc_library {
    defaults: ["native_bridge_stub_library_defaults"],
    name: "libnative_bridge_guest_libGLESv1_CM",
    overrides: ["libGLESv1_CM"],
    stem: "libGLESv1_CM",
    arch: { arm: { srcs: ["stubs_arm.cc"] }, arm64: {...}, riscv64: {...} },
    shared_libs: ["libcutils", "liblog", "libnative_bridge_guest_libEGL"],
}
filegroup { name: "native_bridge_proxy_libGLESv1_CM_files", srcs: ["proxy/gles_trampolines.cc"] }
```

`stem: "libGLESv1_CM"` + `overrides:` means the guest process sees a real `libGLESv1_CM.so`. The
trampoline side is tiny and hand-written (`gles_trampolines.cc`, Copyright 2023):

```cpp
#include "berberis/guest_abi/function_wrappers.h"
#include "berberis/guest_abi/guest_params.h"
#include "berberis/proxy_loader/proxy_library_builder.h"
#if defined(NATIVE_BRIDGE_GUEST_ARCH_ARM) && defined(__i386__)
#include "trampolines_arm_to_x86-inl.h"   // generated file
#elif defined(NATIVE_BRIDGE_GUEST_ARCH_ARM64) && defined(__x86_64__)
...
#else
#error "Unknown guest/host arch combination"
#endif
DEFINE_INIT_PROXY_LIBRARY("libGLESv1_CM.so")
```

**Read this carefully — it is the crux of what RetroBug must add.** `NATIVE_BRIDGE_GUEST_ARCH_ARM`
*exists* as a concept and there is a generated ARM32 stub table, but the only ARM32 *host* pairing is
`__i386__` (the legacy 32-bit emulator). **`arm32 guest → arm64 host` is the missing combination**, and
it is missing in two places:
1. `gen_proxy_libraries.py` (`#!/usr/bin/env python3`, Copyright 2024) enumerates
   `self.arches = { 'arm': '.../symbols/%s/lib/%s.so', 'arm64': '.../lib64/%s.so', ... }` and generates
   stubs by running `dwarf_reader` over built libraries plus `gen_known_trampolines.py` (and
   `gen_vulkan` over `external/vulkan-headers/registry/vk.xml`). It builds `aosp_arm64`, `aosp_x86_64`,
   `aosp_riscv64` source libraries. RetroBug can run the same pipeline; the *ABI lowering* templates
   are what need an arm64 target.
2. Berberis' own `Android.bp` still gates the ARM32 guest default to a 32-bit host:
   `berberis_arm_defaults { compile_multilib: "32", arch: { x86: { cflags: ["-DNATIVE_BRIDGE_GUEST_ARCH_ARM"] } } }`
   — with the standing `TODO(b/123294366): disconnect guest arch from host arch!`
   ([Android.bp:126-135](https://android.googlesource.com/platform/frameworks/libs/binary_translation/+/refs/heads/main/Android.bp)).
   Its README still describes itself as "riscv64 native code on x86_64". **So: Berberis gives RetroBug
   the API-shim architecture and the calling-convention scaffolding, but no ARM32 decoder/backend and
   no arm64-host proxy tables.** That matches doc 02's conclusion (fork Berberis, add an ARM32
   frontend) and adds the API-layer half of that work.

`api_analysis_test.py`, `app_process`, `check_proxy_libraries.py`, `gen_known_trampolines.py`,

## 2. Fixed-function semantics that do not exist in modern pipelines

### 2.1 What must be reproduced

GLES 1.1 state that has no equivalent in a GLES 3.x / Vulkan / Metal pipeline: the matrix stacks and
their modes; the per-vertex colour/material path; two-sided Phong-ish lighting with per-light
attenuation and spot terms; multi-texture-unit environment *combiners* (`GL_COMBINE` with
RGB/alpha sources and operators); per-vertex fog; alpha test; clip planes; point/line rasterization
attributes; and the client-array / immediate-mode input paths.

ANGLE's `GLES1State.h` is the most complete modern inventory of exactly that, and it doubles as a
design checklist. Verified members
([src/libANGLE/GLES1State.h](https://github.com/google/angle/blob/main/src/libANGLE/GLES1State.h)):

| GLES1 feature | ANGLE state |
|---|---|
| Matrix stack | `setMatrixMode`, `pushMatrix`, `popMatrix`, `MatrixStack = angle::FixedVector<Mat4, Caps::GlobalMatrixStackDepth>`, `mProjectionMatrices`, `getCurrentMatrixStackDepth` |
| Lighting | `LightModelParameters`, `LightParameters` (incl. `attenuationLinear`), `MaterialParameters`, `mLightingEnabled`, `setShadeModel(ShadingModel)`, `isColorMaterialEnabled()`, `mColorMaterialEnabled` |
| Texture env combiners | `TextureEnvironmentParameters { mode, combineRgb, combineAlpha, src0Rgb/src1Rgb/src2Rgb, src0Alpha/…, op0Rgb/op1Rgb/op2Rgb, op0Alpha/…, }` — i.e. the full register-combiner triple |
| Fog | `FogParameters { FogMode mode; … }`, `mFogEnabled` |
| Alpha test | `AlphaTestParameters { AlphaTestFunc func; ref }`, `mAlphaTestEnabled` |
| Clip planes | `ClipPlaneParameters(bool enabled, const Vector4& equation)` |
| Points/lines | `PointParameters`, `mPointSizeArrayEnabled`, `mLineSmoothEnabled`, `mPointSmoothEnabled`, `mPointSpriteEnabled` |

Two-sided lighting, normalisation, rescale-normal and draw-texture are all first-class flags, next.

### 2.2 Approach: shader generation, and the size of the problem

`GLES1Renderer.h:14` — *"Defines GLES1 emulation rendering operations on top of a GLES3 context. Used
by Context.h."* The mechanism is a **state-keyed generated-shader cache** (`GLES1Shaders.inc`,
`ShaderProgramManager`), keyed on this bit mask
([src/libANGLE/GLES1Renderer.h](https://github.com/google/angle/blob/main/src/libANGLE/GLES1Renderer.h)):

```cpp
enum class GLES1StateEnables : uint64_t {
    Lighting = 0, Fog = 1, ClipPlanes = 2, DrawTexture = 3, PointRasterization = 4,
    PointSprite = 5, RescaleNormal = 6, Normalize = 7, AlphaTest = 8, ShadeModelFlat = 9,
    ColorMaterial = 10, LightModelTwoSided = 11, LogicOpThroughFramebufferFetch = 12,
    InvalidEnum = 13, EnumCount = 13,
};
```

**Quantified risk:** 13 independent booleans ⇒ **8192** theoretically distinct shader variants, and the
real space is *larger*, not smaller, because texture-unit count, number of active clip planes, fog
mode, and combiner operator tuples multiply in (`TextureEnvironmentParameters` carries 3 sources ×
3 operators × 2 combiners). Every variant is a *different piece of ESSL* that must then be lowered by
the ANGLE back-end to SPIR-V (Vulkan) or MSL (Metal) — so a driver/compiler bug surfaces only for the
apps that happen to use that combination. **That is RetroBug's compat tail**: coverage is sparse and
app-shaped, and it is why §7's differential oracle matters more than any conformance run.
`LogicOpThroughFramebufferFetch` is the tell for how far this reaches into TBDR-specific machinery
(logic ops don't exist in GLES 3.x at all).

**Immediate mode** (`glBegin`/`glEnd`/`glVertex*`) is not in the enables mask because it is not a
shader concern: it is handled as a staging-vertex-buffer accumulation path in `Context_gles_1_0.cpp`
(**inference** from the file's presence + `GLES1State`'s client-array flags; the exact buffering is
not verified here). RetroBug must reproduce it because 32-bit-era games use it heavily; it forces the
API boundary to be *reorderable* — a guest `glEnd()` is the first point at which the primitive can be
issued, which is also why callbacks/pointer lifetimes in §3–§5 matter.

### 2.3 How faithful is ANGLE's GLES 1.1 today? (the brief's core question)

**Status: present, wired into the shipped Android driver, not deprecated, not removed.**
Evidence: (a) the files exist on `main`; (b) `src/libGLESv1_CM/libGLESv1_CM.cpp` (Copyright 2018)
exports the real ES 1.0 entry points (`glAlphaFunc`, `glClearColor`, `glClipPlanef`, `glColor4f`, …)
by tail-calling the autogen'd ES 1.0 dispatch (`GL_AlphaFunc` …) declared in
`libGLESv2/entry_points_gles_1_0_autogen.h` alongside the 2.0/3.2/ext tables; (c) `src/libANGLE/`
ships `validationES1_autogen.h` (ES 1.x validation) and `Context_gles_1_0.cpp`; and (d) most
decisively, AOSP's Mainline module builds `libGLESv1_CM_angle` as a *shippable product* (§1.3).
The brief's "ANGLE reportedly dropped GLES1" is **not supported by the tree**.

Residual quality caveats, all honest: the `a4a_rules.json` mechanism exists precisely because
ANGLE-over-Vulkan is *not* universally safe (rules key on device/GPU/Vulkan driver version, and
`angle_gl_driver_all_angle` is documented by Google as making devices unbootable today); and
GLES 1.x sits on top of a **GLES 3.0** context, so any host GLES3 weakness becomes a guest GLES1
weakness with no way for the app to avoid it. **Unverified:** any published GLES1 conformance/CTS pass
rate for ANGLE's GLES1 layer (dEQP-GLES1 is not in ANGLE's own test doc — §7).

## 3. The windowing / buffer path

### 3.1 What is host-native and what must be 32-bit

Clean split, and the answer to the brief's "which parts can just work":

- **Host-native, effectively free:** the Java-side `SurfaceView` / `TextureView` / `Surface`, the
  `BufferQueue`, gralloc allocation, the producer/consumer scheduling, `AChoreographer`-driven vsync,
  and the actual scanout. RetroBug creates a host `Surface` and hands it to the guest layer.
- **Must exist in 32-bit guest form:** every *handle and struct the guest can dereference* —
  `ANativeWindow*`, `AConfiguration*`, `ALooper*`, `AInputQueue*`, `AInputEvent*`, `android_app`,
  `android_poll_source`, `ANativeActivity` + its callbacks struct, `ANativeWindow_Buffer`,
  `AHardwareBuffer*`, `native_handle_t`. **Must additionally be mirrored, not merely forwarded:**
  `AInputEvent` (see §5.2) and `AConfiguration` (its opaque-to-apps-but-array-backed form).
- **Forwarded by pointer only (opaque, never dereferenced by apps):** `ANativeWindow*`,
  `AHardwareBuffer*`, `EGLSurface`/`EGLContext`/`EGLDisplay`, `SLObjectItf`. These are safe to keep as
  32-bit handle-table indices.

### 3.2 `android_native_app_glue` — reproduce this layout exactly

Games that implement `android_main` link `libnative_app_glue.a` **statically**, so the struct layout is
baked into the guest binary and RetroBug cannot redefine it — it must *emit* the official layout with
32-bit pointers. Verified from
[`platform/ndk/.../native_app_glue/android_native_app_glue.h`](https://android.googlesource.com/platform/ndk/+/refs/heads/main/sources/android/native_app_glue/android_native_app_glue.h)
(lines ~89–200, `refs/heads/main`):

```c
struct android_poll_source { int32_t id; struct android_app* app;
  void (*process)(struct android_app* app, struct android_poll_source* source); };

struct android_app {
  void* userData;
  void (*onAppCmd)(struct android_app* app, int32_t cmd);
  int32_t (*onInputEvent)(struct android_app* app, AInputEvent* event);
  ANativeActivity* activity;   AConfiguration* config;
  void* savedState;            size_t savedStateSize;
  ALooper* looper;             AInputQueue* inputQueue;   ANativeWindow* window;
  ARect contentRect;           int activityState;         int destroyRequested;
  /* private: */ pthread_mutex_t mutex; pthread_cond_t cond;
  int msgread, msgwrite; pthread_t thread;
  struct android_poll_source cmdPollSource, inputPollSource;
  int running, stateSaved, destroyed, redrawNeeded;
  AInputQueue* pendingInputQueue; ANativeWindow* pendingWindow; ARect pendingContentRect;
};
```

`LOOPER_ID_MAIN = 1`, `LOOPER_ID_INPUT = 2`, `LOOPER_ID_USER = 3`; commands
`APP_CMD_INPUT_CHANGED, APP_CMD_INIT_WINDOW, APP_CMD_TERM_WINDOW, APP_CMD_WINDOW_RESIZED,
APP_CMD_WINDOW_REDRAW_NEEDED, APP_CMD_CONTENT_RECT_CHANGED, APP_CMD_GAINED_FOCUS,
APP_CMD_LOST_FOCUS, APP_CMD_CONFIG_CHANGED, APP_CMD_LOW_MEMORY, APP_CMD_START, APP_CMD_RESUME,
APP_CMD_SAVE_STATE, APP_CMD_PAUSE, APP_CMD_STOP, APP_CMD_DESTROY`, with
`android_app_read_cmd` / `android_app_pre_exec_cmd` / `android_app_post_exec_cmd` and
`extern void android_main(struct android_app* app)`.

Traps RetroBug must get right, all implied by that layout:
`size_t savedStateSize` is 4 bytes in guest and 8 in host; `pthread_t`, `pthread_mutex_t`,
`pthread_cond_t` are **inline by value** at a size defined by *guest* bionic, not host bionic; the
two `android_poll_source` members are **embedded**, so their `process` function pointers are guest
addresses that host code must not call directly; and `activityState`/`destroyRequested` are `int`
(not `int32_t`-sized-by-arch, so fine, but must not be re-typed). Since the glue also owns a
`pipe(2)` (`msgread`/`msgwrite`) plus a thread, RetroBug must supply a *guest* `pthread_create` that
enters the translator — the glue's main thread, not the host's.

**The correct reference implementation of the host half is already Apache-2.0 in Berberis:**
`native_activity/native_activity_wrapper.cc`
([link](https://android.googlesource.com/platform/frameworks/libs/binary_translation/+/refs/heads/main/native_activity/native_activity_wrapper.cc))
allocates a **guest-shaped mirror** of the platform struct and wires every host callback into a
`GuestCall`:

```cpp
struct Guest_ANativeActivityCallbacks { GuestAddr onStart; GuestAddr onResume;
  GuestAddr onSaveInstanceState; GuestAddr onPause; GuestAddr onStop; GuestAddr onDestroy;
  GuestAddr onWindowFocusChanged; GuestAddr onNativeWindowCreated; GuestAddr onNativeWindowResized;
  GuestAddr onNativeWindowRedrawNeeded; GuestAddr onNativeWindowDestroyed;
  GuestAddr onInputQueueCreated; GuestAddr onInputQueueDestroyed; GuestAddr onContentRectChanged;
  GuestAddr onConfigurationChanged; GuestAddr onLowMemory; };

struct Guest_ANativeActivity { GuestAddr callbacks; GuestType<JavaVM*> vm; GuestType<JNIEnv*> env;
  jobject activity; GuestAddr internalDataPath; GuestAddr externalDataPath; int32_t sdkVersion;
  GuestAddr instance; GuestAddr assetManager; GuestAddr obbPath;
  ANativeActivity* host_native_activity; };

void Wrap_OnStart(ANativeActivity* activity) {
  Guest_ANativeActivity* ga = ToGuestNativeActivity(activity);          // via activity->instance
  GuestAddr func = GetGuestCallbacks(ga)->onStart; if (func == 0) return;
  GuestCall call; call.AddArgGuestAddr(ToGuestAddr(ga)); call.RunVoid(func); }
```

`GuestType<T*>` is the idiom for "this pointer field is guest-arch-sized" and `ToGuestAddr` /
`ToHostAddr` the cast pair — RetroBug should adopt both verbatim. Note also the `instance`-pointer
trick (host `ANativeActivity::instance` carries the guest struct) and that
`native_activity/include/berberis/native_activity/` ships only `native_activity.h` +
`native_activity_wrapper.h`: **there is no `android_native_app_glue` equivalent for the guest, so
RetroBug must compile the real `android_native_app_glue.c` for ARM32 against guest bionic** (it is
plain C, Apache-2.0, and its only external needs are `libandroid`'s `ALooper`/`AInputQueue` plus
pthread + pipe).

### 3.3 Handles, fds, and fences across 32↔64

Good news first: **`native_handle_t` is arch-neutral.**
[`libcutils/include/cutils/native_handle.h`](https://android.googlesource.com/platform/system/core/+/refs/heads/main/libcutils/include/cutils/native_handle.h):

```c
#define NATIVE_HANDLE_MAX_FDS 1024
#define NATIVE_HANDLE_MAX_INTS 1024
typedef struct native_handle {
    int version;   /* sizeof(native_handle_t) */
    int numFds;    /* number of file-descriptors at &data[0] */
    int numInts;   /* number of ints at &data[numFds] */
    int data[0];   /* numFds + numInts ints */
} native_handle_t;
typedef const native_handle_t* buffer_handle_t;
```

All members are `int`, and fds are small non-negative integers with the *same value* in a 32- and a
64-bit process; `BufferQueue`/`native_handle` transfer happens over binder/`SCM_RIGHTS`, which RetroBug
controls. So the graphics buffer *transport* crosses the boundary essentially for free. Two caveats:
`version` is documented as `sizeof(native_handle_t)` — **same on both arches (16 bytes), so fine**;
and the `numInts` payload is *gralloc private data* whose meaning is vendor- and arch-dependent
(**inference**, but the standard reason `buffer_handle_t` must stay opaque). **Never reinterpret a
handle; keep a guest handle → host handle table.**

Fences: `int sync_wait(int fd, int timeout)` is declared at
`system/core/libsync/include/android/sync.h:45`
([link](https://android.googlesource.com/platform/system/core/+/refs/heads/main/libsync/include/android/sync.h)),
and `sw_sync.h` sits beside it. Fence fds are also just ints, so `EGL_ANDROID_native_fence_sync` /
`AHardwareBuffer` acquire/release fences pass through unchanged. **`android/sync.h` is a deprecated NDK
header**; legacy guests that link it need RetroBug's own shim rather than the host's (unverified
exactly when it left the NDK API surface — §Open questions).

`ANativeWindow_Buffer` is **not** arch-neutral and must be field-marshalled
([`libs/nativewindow/include/android/native_window.h:95-114`](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/main/libs/nativewindow/include/android/native_window.h)):

```c
typedef struct ANativeWindow_Buffer {
    int32_t width; int32_t height; int32_t stride;
    int32_t format;   /* One of AHardwareBuffer_Format */
    void* bits;       /* the actual bits */
    uint32_t reserved[6];
} ANativeWindow_Buffer;
```

Field order is unchanged since at least `android-5.0.0_r1` (verified against that tag's
`native_window.h`, where the same four `int32_t`s precede `bits`; only the `format` *comment* changed
from `WINDOW_FORMAT_*` to `AHardwareBuffer_Format`). But `bits` sits at **offset 20 in a 32-bit build
and 24 in 64-bit**, and the struct is 44 vs 48 bytes: RetroBug must copy width/height/stride/format as
`int32_t`s, translate `bits` (`ToHostAddr`/`ToGuestAddr`), and zero `reserved`. Note the CPU-side
buffer pointer is *shared memory the guest dereferences directly* — so the mapped buffer must live in
the guest's own address space/allocator, not the host's, or be dual-mapped.

Legacy 2D path: `ANativeWindow_lock` / `ANativeWindow_unlockAndPost` /
`ANativeWindow_setBuffersGeometry(window, width, height, format)` (`native_window.h:166,179,188`) are
all still NDK-stable → forward them; formats that matter are `RGBX_8888`/`RGBA_8888`/`RGB_565`, and
the AOSP graphics page separately obliges drivers to **"Support the YV12 image format and other YUV
image formats that come from other components in the system, such as media codecs or the camera"** —
relevant because a legacy camera-preview or video-decode-to-texture app will hand RetroBug YUV, and
external-texture (`GL_OES_texture_external`, also mandated) is how that reaches GLES.

`libjnigraphics.so` (`ABitmap_lockPixels`) is the other legacy CPU-pixel door and is in
`android_api/` (§1.6), so it is cheap to include. `AChoreographer`/`ASurfaceControl`: both live under
`libnativewindow`/`libgui` and are **modern (API 24+ / 29+)** — legacy 32-bit apps essentially never
use them, so RetroBug should treat them as explicitly out of milestone scope (**inference** from API
levels; the CDD library list in §1.1 does not include either).

## 4. Audio

### 4.1 What legacy native code uses, and what the host has

Mandated by the CDD (§1.1) and therefore **present on every modern Android host**: `libOpenSLES.so`
(OpenSL ES 1.0.1) and `libOpenMAXAL.so` (OpenMAX AL 1.0.1). And AOSP generates 32-bit guest shims for
both, plus `libaaudio` and `libamidi` (§1.6). So **forwarding OpenSL ES to host OpenSL ES on Android is
practical by construction** — that is literally what the native-bridge design does.

Corrections to the brief:
- **OpenSL ES on Android does not support MIDI.** The NDK page states it in one sentence: *"OpenSL ES
  for Android does not support MIDI."* ([OpenSL ES for Android](https://developer.android.com/ndk/guides/audio/opensl/opensl-for-android)).
  MIDI is `libamidi.so` / `android/midi.h`, gated on `android.software.midi`. So MIDI-using legacy
  guests are rare and belong to `libamidi`, not `SLEngineItf`.
- **AAudio (API 26+) is indeed irrelevant to 32-bit-era code**, but include the guest `libaaudio` shim
  anyway — it is free, and post-2018 native games use it.
- OpenSL ES is itself **deprecated by Google**: *"WARNING: OpenSL ES is deprecated. Developers should
  use the open source Oboe library"* (same NDK page), and Oboe *"calls AAudio when AAudio is
  available, and falls back to OpenSL ES if AAudio is not."* Deprecation is a maintenance-debt signal,
  not removal — the CDD keeps it mandatory, so the host endpoint stays.
- On "does Android still ship 32-bit OpenSL ES/OpenMAX": on a **64-bit-only** device there is no
  32-bit `/system/lib` userspace GL/audio blob at all — which is *why* the proxy pattern is required:
  the guest's `libOpenSLES.so` is RetroBug's 32-bit shim, and the real implementation it forwards into
  is the host's 64-bit one. **Verified** as an architectural consequence of §1.6 + the CDD list;
  **unverified** for any specific shipping firmware.

`ALoopedBuffer`/OpenMAX AL: same story, one level down (native decoding). It was always thin on the
ground; RetroBug should implement the object-lifecycle skeleton and let `libmediandk` (`AMediaCodec`,
also shimmed) carry real decode work. Java-side `AudioTrack`/`MediaPlayer`/`SoundPool` run on host ART
and need nothing.

### 4.2 What actually breaks when forwarding

OpenSL ES is not a function table — it is a **COM-like object graph**, which is where the work is:

1. **`GetInterface` + `SL_IID_*` GUIDs.** Every object is created via `Create×××` then asked for
   interfaces by IID, and each interface is a pointer-to-a-pointer-to-a-vtable. A guest
   `SLPlayItf` is therefore a 32-bit **vtable of guest-callable thunks** whose entries take guest
   args and tail-call host C++ methods. RetroBug must build that vtable machinery once and reuse it —
   and it must **return the same interface pointer for repeated `GetInterface` of the same IID**,
   because apps compare and cache them. This is the single largest non-GL item in the milestone plan.
2. **Refcounts / `XAObject` lifecycle.** `Realize`/`Destroy`/`SetState` are order- and
   thread-affinity-sensitive, and the engine graph (`SLEngineItf` → OutputMix → players/effects) must
   be *built in the host*, not mirrored — otherwise mixers and effects (`SL_IID_*` for reverb/bass
   boost/preset reverb) silently no-op. **Inference:** the safest first cut is to forward 1:1 into a
   single host engine and validate the effects sub-interfaces later.
3. **Callbacks crossing into emulated code.** `RegisterCallback` hands RetroBug a guest function
   pointer + user `void*`. Every `SLCallback` invocation is a `GuestCall` from a *host* audio-thread,
   which means that thread must be enterable by the translator and, if the callback calls JNI, must be
   `AttachCurrentThread`-able. Consequences: an audio-callback guest frame must not be GC-suspended
   mid-callback, and **guest-side priority/inference of the real-time class does not exist** — a
   low-latency `SL_IID_BUFFERQUEUE` path that used to run at audio-thread priority now runs a
   translated frame. Expect latency and underrun regressions here before any other audio bug.
4. **Buffer queues.** `ENQUEUE`/`DEQUEUE` pass guest PCM addresses; the translator's memory model must
   make those pages host-readable without copying (they are guest-mmap'd, so zero-copy works — but the
   `SLBufferQueueState` count/size and the async index must be marshalled, and `SetBufferInterval`
   semantics differ).
5. **Oboe's migration doc** records the real-world gaps RetroBug inherits if it ever swaps OpenSL ES
   for AAudio: *"Compressed audio … is not supported"*, and OpenSL ES "lacks disconnect mechanisms"
   ([OpenSLES Migration Guide](https://android.googlesource.com/platform/external/oboe/+/a004ac8a65df96fb69fa74b26f32ca9b8e48da86/docs/OpenSLESMigration.md)).

**iOS.** There is no OpenSL ES and no OpenMAX AL. The mapping is
OpenSL ES output-mix/buffer-queue → `AVAudioEngine` + `AURenderCallback`/`AUNode` (or RemoteIO via
AudioToolbox `AudioComponentDescription`), and OpenMAX AL decode → `AVAudioFile`/AudioConverter. This
is a **re-implementation, not a forward**, and the object graph in §4.2 must be re-hosted on it. Practical
consequence: keep a thin internal audio abstraction (engine + players + buffer queues) with two
backends — exactly Oboe's shape, and the reason to *build* that seam in milestone 1 rather than
"just call OpenSL ES directly".

## 5. Input

### 5.1 The legacy surface

Two distinct paths, and the brief's API-level note is half-right:

- **`android_native_app_glue` path (what games use).** `ALooper` + `AInputQueue` +
  `onInputEvent(struct android_app*, AInputEvent*)`. `ALooper_*`/`AEventDispatcher_*` live in
  `libandroid.so` (CDD-mandated, and shimmed with `arch.arm` in `android_api/` — §1.6, §3.1).
  A game's poll loop calls `ALooper_pollOnce` in *guest* code, so RetroBug's guest `ALooper` must
  return guest-side `android_poll_source*` data pointers (§3.2) and honour `LOOPER_ID_MAIN`/`LOOPER_ID_INPUT`.
- **The `AINPUT_JNI_*`/`android_input_event` legacy is *gone from the current header*.** The
  `refs/heads/main` `android_native_app_glue.h` has **no** `struct android_input_event` and no
  `AINPUT_JNI_*` — the modern glue passes `AInputEvent*` straight through. **Inference:** those
  constants belonged to a pre-4.x glue revision; an APK built that old is a separate compat case, and
  RetroBug should confirm against an actual old NDK before implementing anything for it
  (§Open questions). `AMessage` (`android/message.h`) is API 23+ and postdates most 32-bit-era game
  code — low priority.
- **`AInputEvent` accessor API.** The `AInputEvent_getType` / `AKeyEvent_get*` / `AMotionEvent_get*`
  family, plus `AInputQueue_attachLooper`/`getEvent`/`finishEvent`/`preDispatchEvent` and
  `AMotionEvent_fromJava`/`AKeyEvent_fromJava`/`AInputEvent_toJava`, are all `libandroid.so` NDK
  surface ([NDK input reference](https://developer.android.com/ndk/reference/group/input)).
  The accessors are long-stable; **the exact "added in API N" per function could not be pinned from
  the rendered reference page** (it does not expose per-symbol levels in the fetched form) — and the
  `AInputQueue_*` group is treated as legacy. **Do not** rely on any specific level here; enumerate
  symbols from the generated stub list instead (§7.3).

### 5.2 The real hazard: `MotionEvent`/`KeyEvent` cross the boundary as *host C++ objects*

If the guest implements `dispatchTouchEvent` natively (some engines do), it goes through
`libandroid_runtime` — a **private** library, but one AOSP already shims. Its
`stubs_arm.cc` contains the JNI marshalling symbols verbatim
([link](https://android.googlesource.com/platform/frameworks/libs/native_bridge_support/+/refs/heads/main/android_api/libandroid_runtime/stubs_arm.cc)),
e.g. lines 648-649, 311-313, 600-601, 711:

```
_ZN7android37android_view_MotionEvent_getNativePtrEP7_JNIEnvP8_jobject
_ZN7android37android_view_MotionEvent_obtainAsCopyEP7_JNIEnvRKNS_11MotionEventE
_ZN7android41android_view_MotionEvent_obtainFromNativeEP7_JNIEnvNSt3__110unique_ptrINS_11MotionEventENS2_14default_deleteIS4_EEEE
_ZN7android29android_view_KeyEvent_recycleEP7_JNIEnvP8_jobject
_ZN7android10InputQueue17createMotionEventEv
_ZN7android22NativeInputEventSender15sendMotionEventEjPKNS_11MotionEventE
```

Read the signatures. `android_view_MotionEvent_getNativePtr` **returns an `android::MotionEvent*`**
into a `JNIEnv*`-calling context; `obtainFromNative` takes a **`std::__1::unique_ptr<android::MotionEvent,
default_delete<...>>` by value**; `NativeInputEventSender::sendMotionEvent` takes `const android::MotionEvent*`.
So the host hands the guest a pointer to a **host-arch C++ object with host-arch `std` members and
host vtables** — which the guest then reads with `AMotionEvent_getX`. The proxy-stub pattern (forward
the pointer as an opaque word) **does not work here**: `android::MotionEvent`'s field layout differs by
arch, and a by-value `unique_ptr` in a mangled signature cannot be lowered at all.

**Consequence / decision:** RetroBug must own an **ARM32 `AInputEvent` mirror** — allocate a 32-bit
`android::MotionEvent`-shaped object in guest memory (or a private struct plus 32-bit
`AMotionEvent_get*` implementations that read a packed snapshot), fill it from the host event at
dispatch time, and expose guest pointers to *that*. Pointer-identity constraints to honour:
`AMotionEvent_fromJava`/`AInputEvent_toJava` interop, `AInputEvent_release`, and the fact that
`android_view_MotionEvent_recycle`/`obtainAsCopy` imply apps cache and recycle. That is bounded work
( MotionEvent has a fixed, well-documented accessor set) but it is **not** a proxy stub, and it is the
second-largest correctness risk after §2. Mark `libandroid_runtime` as **milestone-2**, not
milestone-1: games using it natively are a minority, and the `NativeActivity`/glue path (§5.1) does
not need it.

### 5.3 Touch injection and the on-screen control layer

Because guest input arrives through RetroBug's own `AInputQueue` shim, RetroBug has exactly one
injection seam, and it should be a single function: *host `MotionEvent` (or synthetic) → guest
`AInputEvent` mirror → `LOOPER_ID_INPUT` wake-up*. Everything else composes onto it:

- Physical gamepads / keyboards: host `MotionEvent`/`KeyEvent` → the same seam (set `source`,
  `deviceId`, axis values so the guest's own deadzone code behaves).
- **On-screen overlay controls: implement them host-side in the app's own UI layer**, as a transparent
  view over the `SurfaceView`, synthesising multi-pointer `MotionEvent`s into the seam. Never inject at
  the GL layer and never via `/dev/input` (`input_event` from `struct input.h` is a **kernel** ABI that
  Android apps do not read — the brief's own suspicion is correct; there is no reason for RetroBug to
  emulate it).
- This seam is also the replay/record hook: log serialised injected events per frame for the
  reproducible-bug reports doc 08's "send us your broken app" flow needs.
- Prior art in-house: doc 08 points at `OnScreenController.kt` (single reusable view, scale clamp
  0.5–2.0, haptics, menu-passthrough hook) and the iOS virtual pad in `XenraAppDelegate.mm`, plus the
  first-touch stick-anchor bug and the physical-pad registry with player-1 fallback — reuse that
  design rather than re-deriving it.

## 6. iOS-specific bridging, and the one-backend question

### 6.1 MoltenVK facts

Verified from the **locally vendored copy**
(`xaniteOG/XenDroid/emulator-core/src/main/cpp/xenia/third_party/MoltenVK/`, version **1.4.2**, `Docs/Whats_New.md`),
confirmed against upstream:

- **License: Apache-2.0** (local `LICENSE` is the standard Apache text). Not BSD-3.
- Self-description: *"a layered implementation of Vulkan 1.4 graphics and compute functionality, built
  on Apple's Metal"*, explicitly **a Vulkan 1.4 *subset***; compliance is graded as *direct mapping* /
  *synthesized compliance through alternate implementation* ("a small amount of capability … such as
  via an extra render or compute shader stage") / (remaining category truncated in the fetched view).
- **`VK_KHR_portability_subset` is supported, and that has a sharp edge:** with the Vulkan SDK loader,
  MoltenVK's physical devices *"will only [be returned] … if the
  `VK_INSTANCE_CREATE_ENUMERATE_PORTABILITY_BIT_KHR` flag is enabled in `vkCreateInstance()`."* A guest
  Vulkan binary compiled against an Android conformant driver will **not** set that flag → zero devices
  enumerated → silent init failure. **RetroBug must intercept `vkCreateInstance` in the guest
  `libvulkan` proxy and force the portability-enumeration bit** (linking MoltenVK directly, without a
  loader, sidesteps only the loader's filtering, not the portability caveats themselves).
- Documented limitations (local `Docs/MoltenVK_Runtime_UserGuide.md:676-690`): PVRTC images must be
  loaded by host-visible mapping (a staging-buffer upload yields *"malformed image content"*);
  `VK_QUERY_TYPE_PIPELINE_STATISTICS` unsupported; `VkAllocationCallbacks` **ignored**; MoltenVK does
  not itself load Vulkan layers (so *validation layers require the SDK loader* — relevant to §7).
- Tuning knobs live in `Docs/MoltenVK_Configuration_Parameters.md` — notably
  `MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS`, `MVK_CONFIG_SYNCHRONOUS_QUEUE_SUBMITS`,
  `MVK_CONFIG_USE_COMMAND_POOLING`, `MVK_CONFIG_SHADER_CONVERSION_FLIP_VERTEX_Y`,
  `MVK_CONFIG_TEXTURE_1D_AS_2D`, `MVK_CONFIG_RESUME_LOST_DEVICE`, `MVK_CONFIG_SPECIALIZED_QUEUE_FAMILIES`,
  `MVK_CONFIG_API_VERSION_TO_ADVERTISE`, `MVK_CONFIG_TRACE_VULKAN_CALLS`, `MVK_CONFIG_DEBUG`.
  `SHADER_CONVERSION_FLIP_VERTEX_Y` and `TEXTURE_1D_AS_2D` are the two that most often show up as
  guest-visible rendering differences.
- **Not verified in this pass:** timeline semaphores and sparse binding. MoltenVK has had emulated
  timeline semaphores for some time and has never supported sparse binding, but neither appears in the
  local limitations section, so RetroBug should *measure* both at init rather than assume. Per doc 08's
  rule ("probe capabilities at init and report requested vs active"), add them to the GPU-probe
  checklist alongside `VK_KHR_swapchain`-on-`CAMetalLayer`.

Two structural notes carried over from the local prior-work audit, because they shape the iOS plan:
MoltenVK **does not provide EGL**, so an Android-style EGL/GLES compositing layer must not sit under the
swapchain (the OG-iOS plan's fix was to let the Vulkan swapchain own presentation through an
externally supplied `CAMetalLayer`); and on iOS the **shader/AIR target** is the failure mode, not the
API — `MVK_CONFIG_SHADER_*`/`metallib` builds must emit `iphoneos`-targeted bytecode (doc 08,
"Vulkan→Metal lessons" 4).

### 6.2 One Vulkan backend, or GLES-native + Metal?

The brief's option list, evaluated:

| Option | Pros | Cons / evidence |
|---|---|---|
| **A. Vulkan as the single host backend** (GLES→Vulkan on both platforms; MoltenVK on iOS) | One host API to write against; matches the dev's proven Vita3K/MoltenVK muscle memory; "bridge first, native later" is the documented preference *when the Vulkan path is battle-tested* (doc 08, Vulkan→Metal 1) | **On Android it inserts a translation in front of a driver that already implements GLES natively** and is CDD-mandated to do so (§1.1) — pure overhead plus ANGLE's GLES1 variant explosion (§2.2) *and* ANGLE's Vulkan-back-end bugs, both owned by RetroBug. Inherits MoltenVK's portability subset on iOS anyway. Requires host-Vulkan-existence assumptions Android does not guarantee (`[C-SR-*]` only *recommends* Vulkan). |
| **B. GLES-native on Android / ANGLE→Metal on iOS** | Zero extra translation where a conformant driver is guaranteed; preserves per-app fallback to the *vendor* driver; nothing new to validate for the 90% case | Two backends to keep semantically equal; iOS needs ANGLE maintenance; GLES1 fidelity differs between the two paths (a *test* problem, §7) |
| **C. ANGLE as the single front-end; back-end chosen per platform** (GLES1/2/3 → `renderer/vulkan` on Android, → `renderer/metal` on iOS) + guest Vulkan forwarded natively | One *translation* codebase (ANGLE), which already ships both back-ends, already ships GLES1 on top of a GLES3 context, and is already Android's own alt-driver; iOS never touches deprecated GL; per-platform we pick whichever ANGLE back-end is healthiest — and can even pick per-app (`angle_gl_driver_selection_values` semantics) | RetroBug owns an ANGLE fork; must marshal ANGLE's EGL/`Surface` assumptions on iOS; two back-ends still exist, they are just both inside ANGLE |

**Recommendation: C, with B's default behaviour.** Concretely: **forward to host GLES by default on
Android** (optionality is nearly free once the proxy layer exists, and the CDD makes it sound), expose
**ANGLE as a per-app host backend override** (`angle`/`native`/`default`, reusing Google's
settings+rules-file shape), and on **iOS use ANGLE's Metal back-end** as the only GL path — with guest
**Vulkan** kept on a *separate* path (host Vulkan on Android, MoltenVK on iOS, portability bit forced).
Reject A: routing guest GLES through a single Vulkan host API doubles the translation depth for no
correctness gain on Android, and the MoltenVK portability-subset problems it buys on iOS are not
avoided by it. This is also the option that costs the *least* of the dev's MoltenVK experience —
iOS guest-Vulkan still goes through MoltenVK, so that muscle memory is used where it actually helps.

## 7. Testing faithfulness

### 7.1 RetroBug's unfair advantage: the host driver is the oracle

Dolphin and PPSSPP have no reference implementation — they compare to *real hardware*, and their
graphics regressions are built as replay-and-diff harnesses over curated scenes with a frame-accumulator
/ hash-and-screenshot pipeline (**inference from general knowledge; not verified in this pass**).
RetroBug's situation is *better*: on Android the host has a **CDD-mandated GLES 1.1–3.1 driver**
(§1.1). So the primary loop is differential, not golden-file:

1. Run the *same ARM32 object code* twice: (a) guest→proxy→**host driver**, (b)
   guest→proxy→**ANGLE/`libGLESv1_CM_angle`**→Vulkan→(host\|SwiftShader).
   Byte-compare the read-back framebuffer.
2. Run path (b) on desktop with the **Vulkan validation layers** + ANGLE's dEQP harness, then again on
   device. Divergence between (a) and (b) is *by definition* a RetroBug/ANGLE-side fidelity bug or a
   driver bug — and it is reproducible from a recorded API trace.
3. Third leg for determinism: **SwANGLE (ANGLE→SwiftShader)**, all Apache-2.0/BSD and CPU-only, giving
   bit-stable references with no GPU in the loop (§1.5, §6.1: SwiftShader is Vulkan-only today, so GL
   reachability *requires* ANGLE — which is exactly why RetroBug should adopt SwANGLE rather than
   "SwiftShader GLES").

Frame comparison should be tiered, because TBDR-vs-TBDR and MSAA-vs-no-MSAA legitimately differ:
exact-hash (deterministic leg), then per-pixel RMSE threshold, then perceptual (SSIM) for
filtering/order-dependent cases, with an explicit `expected-diff` allow-list keyed by (app, GPU,
backend) — the same per-title-override discipline doc 08 documents (`GAME_COMPAT.md` sections, and
"echo effective values at load").

### 7.2 Reuse the suites Android itself uses

- **dEQP**, per the CDD: test lists live at `external/deqp/android/cts/main/glesXX-master-YYYY-MM-DD.txt`
  and `vk-master-YYYY-MM-DD.txt`; support is declared through
  `android.software.opengles.deqp.level` / `android.software.vulkan.deqp.level`, and `[C-2-4]`/`[C-2-5]`
  make `132383489` (2020-03-01) the floor devices must pass **for each supported GLES version** —
  i.e. an existing, versioned, GLES-1.x-inclusive test corpus RetroBug can run against its own front-end.
  AOSP's own guidance is at [drawElements Quality Program testing](https://source.android.com/docs/core/graphics/deqp-testing).
- **ANGLE's dEQP integration**, [`chromium.googlesource.com/angle/angle → doc/dEQP.md`](https://chromium.googlesource.com/angle/angle/+/main/doc/dEQP.md):
  ANGLE runs dEQP GLES2/GLES3/EGL functional suites with filters such as
  `dEQP-GLES2.functional.shaders.linkage.*`. **Caveat found:** that doc does **not** show a GLES 1.x
  suite — so dEQP coverage of ANGLE's GLES1 layer is thin and RetroBug cannot outsource §2's risk to
  it. This is the concrete gap RetroBug's own GLES1 corpus must fill.
- **VCT**: the Vulkan CTS is `KhronosGroup/Vulkan-CTS` (successor to dEQP-VK; dEQP-VK remains the
  common name) — use it to gate the guest-Vulkan→MoltenVK path, and note MoltenVK is a *subset*, so
  expect to maintain an exclusion list, not a pass/fail.
- **GTF** (Linaro/GTF): named in the brief; **not verified in this pass** — treat as optional.
- **CTS**: not directly runnable by RetroBug (it tests the device), but the *feature-flag* declarations
  above are the vocabulary RetroBug should spoof consistently (§doc 02's `CPU_ABI` spoofing point).

### 7.3 Cheap high-yield tests to build in milestone 1

1. **API-completeness test**: diff the symbols the guest proxies export against what the *real* NDK
   library exports, per API level. AOSP already ships the tooling: `android_api/api_analysis.py`,
   `api_analysis_test.py`, `check_proxy_libraries.py` (§1.6). A missing symbol is a crash; an
   unimplemented stub returning `GL_NO_ERROR` is a silent wrong-picture bug, so the test must assert
   *implemented*, not merely *present*.
2. **First-frame smoke test** (§Minimum viable surface): for each app in the compat corpus, assert
   `APP_CMD_INIT_WINDOW` → non-black framebuffer with >N distinct colours → ≥1 `eglSwapBuffers`
   → guest `android_main` still alive at frame K. This catches 80% of API-layer bugs and is the CI gate
   that scales to hundreds of APKs.
3. **Input round-trip test**: inject a scripted 2-pointer gesture through the §5.3 seam, assert the
   guest-visible `AMotionEvent_get*` values equal the injected ones exactly (pointer index packing,
   `getHistorical*`, `downTime`/`eventTime` monotonicity). Input marshalling bugs are invisible in
   screenshots.
4. **Trace-and-replay**: record every guest→proxy call (args, guest pointers, thread id) to a
   ring buffer; on crash, dump the last N calls plus the ANGLE `GLES1StateEnables` mask. That single
   mask is the most valuable diagnostic in §2's world — it turns "some game renders wrong" into "the
   Lighting|ColorMaterial|LightModelTwoSided variant is wrong", which is an ANGLE-file-scoped bug.
   Design it as a `debug.retrobug.*` property per doc 08's P8 (A/B without rebuilds) and keep the
   conformance-build idea (backend forced to fallback so a fault is attributable in one build).
5. Reuse the **GPU capability probe** pattern from doc 08 (`vulkan_diagnostics.cc`: ordered candidate
   paths, report rewritten after *every* append so it survives a hang, REQUIRED markers,
   `>>> INITIALIZATION FAILED AT: <stage> <<<`) for the GLES/EGL/audio backend selection report.

## Minimum viable API surface for milestone 1

Goal: a `NativeActivity` 32-bit game reaches a correct first frame with touch, plus a CPU-blit 2D app.
Everything here is either a CDD-mandated library (§1.1) or has a generated `arch.arm` shim (§1.6).

**Must exist as 32-bit guest objects (dereferenceable by guest code)**
1. `struct android_app`, `struct android_poll_source`, `LOOPER_ID_*`, all `APP_CMD_*`,
   `android_app_read_cmd`/`pre_exec_cmd`/`post_exec_cmd`/`exec_cmd`, `android_main` entry — i.e. the
   official `android_native_app_glue.c` compiled for ARM32 against guest bionic (§3.2).
2. `Guest_ANativeActivity` + 16-callback `Guest_ANativeActivityCallbacks` (Berberis layout, §3.2).
3. `ANativeWindow_Buffer` with `bits` at guest offset 20 (§3.3); `ARect` (`contentRect`).
4. `ALooper*` (incl. `ALooper_pollOnce`/`pollAll`, `ALooper_acquire`/`release`,
   `ALooper_addFd`/`removeFd`, `ALooper_forThread`), `AInputQueue*`
   (`attachLooper`/`detachLooper`/`getEvent`/`finishEvent`/`hasEvents`/`preDispatchEvent`).
5. **The ARM32 `AInputEvent`/`AMotionEvent`/`KeyEvent` mirror** with the `AInputEvent_getType`,
   `AMotionEvent_get{X,Y,Action,PointerCount,PointerId,EventTime,DownTime}`, `AKeyEvent_get{KeyCode,Action}`
   accessors (§5.2 — this is unavoidable; it is not a proxy stub).
6. `AConfiguration*` mirror, or a documented refusal path.

**Forwarded-by-handle (opaque) into host 64-bit stacks**
7. `libEGL`: `eglGetDisplay`, `eglInitialize`, `eglTerminate`, `eglChooseConfig`, `eglGetConfigs`,
   `eglCreateContext`, `eglCreateWindowSurface`, `eglMakeCurrent`, `eglSwapBuffers`, `eglSwapInterval`,

   `eglDestroyImage`/`eglCreateImageKHR` (`EGL_KHR_image_base`) and
   `eglCreateWindowKHR`-family left to milestone 2.
8. `libGLESv1_CM`: the full ~140-function ES 1.1 set is the honest target, but the first-frame subset
   is `glEnable`/`glDisable`/`glPushClientAttrib`, `glMatrixMode`/`glLoadIdentity`/`glLoadMatrixf`/
   `glOrthof`/`glFrustumf`/`glViewport`/`glScissor`, `glClearColor`/`glClear`, `glGenTextures`/

   `glGetError`/`glGetString`, `glFlush`/`glFinish`.

10. `libandroid`: `ANativeActivity_*`, `ANativeWindow_*` (`acquire`/`release`/`lock`/

mask diagnostic), and every extension beyond `GL_OES_texture_external`/`EGL_KHR_image_base`/
`EGL_KHR_fence_sync`.

## Backend strategy recommendation

Run the guest GL/audio/input layer as **generated 32-bit proxy libraries that forward to the host's
native 64-bit stack by default**, built on AOSP's `native_bridge_support/android_api` stub-generation
machinery (Apache-2.0, already contains `arch.arm` variants of `libEGL`/`libGLESv1_CM`/`libGLESv2`/
`libGLESv3`/`libOpenSLES`/`libOpenMAXAL`/`libandroid`/`libandroid_runtime`/`libnativewindow`/
`libjnigraphics`/`libvulkan` — RetroBug writes ABI lowering, not API surface), because the Android 16
CDD still *mandates* GLES 1.1–3.1 plus OpenSL ES/OpenMAX AL on every host, so on Android "forward,
don't translate" is both legal and cheap. Layer **ANGLE as a per-app selectable host back-end**
(AOSP already ships `libEGL_angle`/`libGLESv1_CM`/`libGLESv2_angle` as a Mainline module with a
`angle`/`native`/`default` + rules-file selection interface to copy), and on **iOS make ANGLE's
`renderer/metal` the only GL path** — since Apple deprecated GL at iOS 12, never shipped it on
visionOS, and offers no GLES 1.x guarantee on current silicon, so ANGLE's GLES1-on-GLES3 renderer
(`GLES1State`/`GLES1Renderer`/`GLES1Shaders.inc`) is what buys iOS parity *and* the Android escape
hatch from one codebase. Keep guest **Vulkan on its own separate path** — forward to host Vulkan on
Android, and to MoltenVK (Apache-2.0, Vulkan-1.4-subset) through an externally supplied `CAMetalLayer`
on iOS, **force-intercepting `vkCreateInstance` to set
`VK_INSTANCE_CREATE_ENUMERATE_PORTABILITY_BIT_KHR`** because MoltenVK advertises
`VK_KHR_portability_subset` — and use **SwANGLE (ANGLE→SwiftShader, Apache-2.0, Vulkan-only today)** as
the deterministic, GPU-free reference renderer for golden-image CI. Reject the "single Vulkan host
backend" idea: it inserts a GLES→Vulkan translation in front of a driver that is already
required to implement GLES natively, doubles the correctness surface, still cannot dodge MoltenVK's
portability caveats on iOS, and rests on a Vulkan guarantee Android does not actually make.
