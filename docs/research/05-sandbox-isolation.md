# 05 — Sandbox isolation: per-guest-instance filesystem, network, and settings isolation without a VM

**Question:** what isolation primitives exist on Android (and iOS) that let **one unprivileged app process** enforce per-emulated-guest-instance filesystem, network, and settings isolation — and how strong is each really?

**Method:** primary sources only — AOSP on `android.googlesource.com` (`system/sepolicy`, `bionic`, `frameworks/base`, kernel uapi headers), the Linux kernel docs/man-pages upstream, Android and Apple developer documentation, and published security research. Every claim is cited. Statements marked **[inference]** are my reasoning from cited facts, not a cited source. Marked **[UNVERIFIED]** means I could not find a primary source in this pass.

Research date: 2026-09. Trees read: `system/sepolicy` @ `refs/heads/main` and @ `refs/heads/android15-release`; `bionic` @ `refs/heads/main`; `frameworks/base` @ `refs/heads/main`.

**Scope reminder.** RetroBug's *normal* path is in-process in one ordinary unprivileged app. The material below is for the *optional, per-app isolated environment*. The product commitments to be **verified, not assumed** are: one-app scope, network-off-by-default with per-app explicit opt-in, fully separate filesystem, isolated settings in that app's own profile, a distinct subsystem with its own lifecycle, and never-default / deliberate-visible entry.

## 1. Syscall-level (in-monitor) mediation as the primary enforcement point

### 1.1 Why the syscall layer is the only place enforcement can be sound

Guest ARMv7 code never executes on the host CPU. Every kernel-visible action it takes reaches the host kernel **only because RetroBug's dispatcher decided to make a host syscall on its behalf**. That makes the syscall layer the only place where all four isolation requirements (filesystem, network, settings, cross-instance) can be enforced from a single, auditable decision point — the classic "complete mediation" requirement (Saltzer & Schroeder, *The protection of information in computer systems*, Proc. IEEE, 1975; [ACM DL classic](https://dl.acm.org/doi/10.1145/354920.354939)).

Soundness requires three things, and the third is the one projects skip:

1. **Default-deny dispatch.** The dispatcher must be an allowlist keyed on the guest syscall number, with the *unknown* case being "refuse + log", never "forward". This mirrors what Android itself does at the kernel boundary (§2.6): the generated app filter is built from the syscall set bionic actually implements.
2. **No host-side side channels.** In-process mediation is bypassed by anything that reaches the kernel *without* going through the dispatcher. Concretely, on Android:
   * **already-mapped shared memory**: `/dev/__properties__` — `__system_property_find()/read()` walk an `mmap`'d region and perform **no syscall per lookup**, so a property read is invisible to the monitor ([bionic `__system_property_get.cpp`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/bionic/__system_property_get.cpp)); plus `/dev/ashmem`/`memfd` regions, `MAP_SHARED` file mappings and System V `shm`.
   * **host library calls reached through shims**: RetroBug's JNI/libc shims run host code directly. If one shim calls `open()` on a guest-supplied path, the entire VFS layer is bypassed. Every shim that takes a path, an fd, a socket, or a `jstring` filename must funnel through the same resolver.
   * **inherited/host-side fds** (ambient authority): a host fd that survives into the guest's visible fd table is a capability the guest can use without ever asking (§1.3, last rows).
3. **A kernel backstop.** In-process mediation alone is *not* sound against a bug in the monitor: one flaw in RetroBug's resolver and the guest has host `open()`. The mitigation is to also install a real seccomp-bpf filter on the sandbox thread/process (§2.6) mirroring the monitor policy, so a monitor bug becomes `SIGSYS` instead of an escape. Android explicitly permits an app to install its own filter: `seccomp(unsigned, unsigned, void*)` is in the **common allowlist** with the comment "Needed for a CTS test of seccomp (b/34763393)" ([`bionic/libc/SECCOMP_ALLOWLIST_COMMON.TXT`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/SECCOMP_ALLOWLIST_COMMON.TXT)).

Guest numbers below are **ARM EABI (32-bit `armeabi-v7a`)** syscall numbers, verified against [`arch/arm/tools/syscall.tbl`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/arch/arm/tools/syscall.tbl) (fetched 2026-09, `common`/`eabi` rows). | IPC (cross-instance) | `ipc` 164 (System V `shmget`/`shmat`/`msgsnd`/`semop`), `memfd_create` 385, `shm_open`, `mq_open`, `mq_timedsend` 274, `mq_timedreceive` 275, `add_key`/`request_key`/`keyctl` | SysV IPC, POSIX MQ and the **kernel keyring are UID-scoped**: two instances in one app UID share them by construction | deny, or namespace guest-visible ids; assume anything UID-scoped is shared (§2.3, §2.9) |
| Async I/O | `io_setup` 243, `io_destroy` 244, `io_submit` 245, `io_cancel` 246, `io_getevents` 248, `io_uring_setup` 425, `io_uring_enter` 426, `io_uring_register` 427 | `IORING_OP_OPENAT`/`OPENAT2`/`STATX`/`UNLINKAT`/`RENAME`/`LINK` = **a second syscall interface that skips the monitor entirely** | deny legacy aio in guest ABI; `io_uring` is unreachable from a host app anyway (§1.4) |
| Timing/covert | `timerfd_create` 350, `eventfd` 351 / `eventfd2` 356, `signalfd` 349, `select`/`pselect6` 355, `poll`/`ppoll` 336, `epoll_*` | not isolation holes alone, but `eventfd` + SysV shm are cross-instance covert channels | allow; document in the threat model |

**Oracle discipline [design rule].** Refusals must be indistinguishable between "does not exist" and "not allowed", or guest code can enumerate the host filesystem through `faccessat`/`stat` errno differences. Return one errno (`ENOENT`) for everything not visible to this instance, and keep the failure path's latency similar.

### 1.3 Classic escape routes and their mitigations

| Escape route | Mechanism / evidence | Mitigation |
|---|---|---|
| `..` traversal | `openat(fd, "../../../etc/…")`; `..` resolves against the *directory a link references*, which is what makes `/proc` magic-link walks dangerous ([`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html), [`proc_pid_root(5)`](https://man7.org/linux/man-pages/man5/proc_pid_root.5.html)) | resolver clamps `..` at the instance root (POSIX `chroot` semantics: `/.. == /`); `..` is never resolved by string surgery but by a parent-dirfd walk RetroBug itself controls |
| Symlink TOCTOU between `lstat` and `open` | guest checks `lstat`, then opens; the target can change in between | RetroBug resolves internally, so it keeps the resolved identity in a host fd: never implement `stat`-then-`open`; implement `open`-then-`fstat` and synthesise the `lstat` answer from VFS state |
| Symlink at open time | `O_NOFOLLOW` protects only the **final** component — man page: "If the trailing component … is a symbolic link, then the open fails, with the error ELOOP. Symbolic links in earlier components of the pathname will still be followed" ([`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html)) | resolve every intermediate component from in-instance dirfds; refuse any symlink whose target cannot be re-expressed as a guest path inside the root |
| `ELOOP` ambiguity | man page notes the `O_NOFOLLOW` ELOOP is "indistinguishable from … too many symbolic links found while resolving components in the path prefix" | keep separate loop budgets (per-component vs total) so the reason is knowable internally while presenting a single guest-visible errno |
| Magic-link opens (`/proc/self/fd/N`, `/proc/self/cwd`, `/proc/self/root`) | these are symlinks to the *current* file/inode, so opening them re-opens the target regardless of the original pathname; access to another process's copies is gated by `PTRACE_MODE_READ_FSCREDS` — for your **own** process there is no gate ([`proc_pid_root(5)`](https://man7.org/linux/man-pages/man5/proc_pid_root.5.html): "Permission to dereference or read (readlink(2)) this symbolic link is governed by a ptrace access mode PTRACE_MODE_READ_FSCREDS check"; [`proc_pid_fd(5)`](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html)) | **the host `/proc` must never be reachable from the guest**; serve a synthetic `/proc`. `readlink("/proc/self/fd/N")` must return the *guest* path — a host path returned here is immediately re-openable. RetroBug's own internal fds (config, code cache, **other instances' roots**) are visible in the real `/proc/self/fd`, so any guest-reachable host `/proc` is a total break |
| Hardlink escape | `linkat` with `AT_EMPTY_PATH` on an `O_PATH` fd, or `link("/proc/self/fd/N", dst)` — turns an fd into a name | deny `AT_EMPTY_PATH` except for in-instance regular files verified via the capability table; refuse `link*` when the existing file's `(st_dev, st_ino)` is not in the instance set |
| Delegating isolation to `openat2(RESOLVE_IN_ROOT)` | man page: `RESOLVE_IN_ROOT` "Treat the directory referred to by dirfd as the root directory" ([`openat2(2)`](https://man7.org/linux/man-pages/man2/openat2.2.html)) — attractive, but see §1.4 | **cannot be depended on**: the syscall is outside Android's app allowlist. Implement `RESOLVE_IN_ROOT` semantics ourselves; use the kernel call only as an extra layer on non-Android hosts (dev/CI) |
| `MAP_SHARED` onto a host file | writes land in the host file even after `close`; a `MAP_SHARED` of a file RetroBug itself uses (config, translated-code cache) corrupts monitor state | `mmap(fd, MAP_SHARED)` requires: fd in the capability table + `fstat` identity inside the instance tree + guest write access. RetroBug-internal files must never have their host fd in the table at all |
| `SCM_RIGHTS` fd passing | `sendmsg`/`recvmsg` cmsg `SCM_RIGHTS` injects arbitrary fds into a process | parse `msg_control` on **both** directions for guest-owned sockets and refuse `SCM_RIGHTS`; never `recvmsg` from a guest-touchable socket into the host fd table |
| Binder `/dev/binder` ioctls | `BINDER_WRITE_READ` with `BINDER_TYPE_FD` moves fds to/from host services — a path around the whole FS layer | guest-visible binder only via RetroBug's IPC shim: never accept inbound fds beyond a small allowlist (e.g. `native_handle` from SurfaceFlinger), and convert every inbound fd into a capability-table entry immediately, never returning a raw host fd |
| Inherited open fds (ambient authority) | fds survive `fork()`; `O_CLOEXEC` is not the default, and setting it afterwards races with `fork`+`execve` — man page: "using a separate `fcntl(2)` F_SETFD operation to set the FD_CLOEXEC flag does not suffice to avoid race conditions where one thread opens a file descriptor and attempts to set its close-on-exec flag … at the same time as another thread does a `fork(2)` plus `execve(2)`" ([`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html)) | (1) every host open uses `O_CLOEXEC`, and pipes/eventfds use `*_CLOEXEC`; (2) **fd-space offset**: guest fd *n* ↔ host fd *n+BASE*, so guessed numbers hit `EBADF` and the two spaces are separable by inspection; (3) `instance_id` validated on every table lookup, so a cross-instance fd value can never resolve |
| Device nodes and shared paths | `/dev/ashmem`, `/data/local/tmp`, `/sdcard`, world-writable cache dirs | the instance mount table must contain **no writable shared mount**; `android_data_file`/`obb`/`media` are the usual accidental shared scratch — exclude them |
| UID-scoped global state | kernel keyring, System V IPC, POSIX MQ, `/proc/net/*` are per-UID/per-netns | deny in guest ABI; treat as shared-by-construction between same-UID instances (§2.3, §2.9) |
| `perf_event_open`, `userfaultfd`, `kcmp`, `process_vm_*` | all four are *allowed* to Android apps (in `SYSCALLS.TXT` and re-allowed by [`SECCOMP_ALLOWLIST_COMMON.TXT`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/SECCOMP_ALLOWLIST_COMMON.TXT): `perf_event_open … all`, `userfaultfd(int) all`, and the `seccomp`/`clone3` entries) | deny in the guest ABI; add them to RetroBug's own child filter for the isolated environment (§2.6) |

### 1.4 `openat2` / `RESOLVE_*` on Android — **not available to an app process**

* `openat2` **does** exist in the **ARM EABI** table at number **437** (`common openat2`), with `faccessat2` 439 and `close_range` 436 ([`arch/arm/tools/syscall.tbl`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/arch/arm/tools/syscall.tbl)). Upstream introduced it in Linux 5.6 ([`openat2(2)`](https://man7.org/linux/man-pages/man2/openat2.2.html)), so Android 13+ kernels generally implement it.
* Android's **app** seccomp filter is generated as `final allowlist = SYSCALLS.TXT − SECCOMP_BLOCKLIST_*.TXT + SECCOMP_ALLOWLIST_*.TXT` — stated verbatim in [`bionic/libc/SECCOMP_BLOCKLIST_APP.TXT`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/SECCOMP_BLOCKLIST_APP.TXT); `SYSCALLS.TXT` is "used to automatically generate bionic's system call stubs" ([`bionic/libc/SYSCALLS.TXT`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/SYSCALLS.TXT)); consumed by [`libc/tools/genseccomp.py`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/tools/genseccomp.py) (`merge_names()` = `(base_names - blocklist_names) | allowlist_names`), installed by [`libc/seccomp/seccomp_policy.cpp`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/seccomp/seccomp_policy.cpp) for zygote-spawned processes.
* **`openat2` is not in `SYSCALLS.TXT`** — grepping `refs/heads/main` for `openat2`, `faccessat2`, `landlock_*`, `io_uring_*`, `pivot_root` returns **zero** hits, while `close_range` (122), `copy_file_range` (123), `memfd_create` (125), `linkat` (167), `renameat2` (171), `statx` (231), `setns` (326), `unshare` (327), `process_vm_readv` (354), `pidfd_getfd` (391) **are** present.
* Because seccomp filters can only get *stricter* — a process may install more filters but never remove installed ones ([Seccomp filter in Android O](https://android-developers.googleblog.com/2017/07/seccomp-filter-in-android-o.html)) — RetroBug cannot re-enable them. **[inference, from "not in the generated allowlist" + "filters are cumulative"]**: calls to these numbers from an app process are not permitted. **This must be empirically confirmed on a device** (T-13 in the test plan) because the generated BPF's fall-through action deserves a direct observation rather than my reading of `genseccomp.py`.

**Consequences.**
1. RetroBug must implement path resolution itself; the kernel's `RESOLVE_IN_ROOT` cannot be the enforcement primitive.
2. **Landlock** — unprivileged, inode-based, path-below-a-dir-fd access control ([kernel docs: Landlock: unprivileged access control](https://docs.kernel.org/userspace-api/landlock.html)) — is dead for the same reason (syscalls 444-446, not in `SYSCALLS.TXT`), independent of whether shipped Android kernels enable `CONFIG_SECURITY_LANDLOCK` **[UNVERIFIED]**. Worth the device test: if any OEM build permits it, Landlock is an unusually good second layer precisely because it constrains by inode, so symlink/`..` tricks are irrelevant.
3. **`io_uring` is not a bypass risk on Android** (425-427 absent) — a rare piece of good news, since io_uring is the modern way to defeat a seccomp-based sandbox.
4. Guest-side: RetroBug should still *implement* `openat2(437)` semantics (including `RESOLVE_BENEATH`/`IN_ROOT`/`NO_SYMLINKS`/`NO_MAGICLINKS`/`NO_XDEV`) because its resolver is a faithful `RESOLVE_IN_ROOT` implementation anyway; refusing it outright would break newer guest `.so`s that probe for it, and `openat2` was specifically designed so callers can distinguish unsupported flags instead of silently ignoring them ([LWN: open: introduce openat2(2) syscall](https://lwn.net/Articles/804980/)).

### 1.5 Design of the virtualized guest VFS

1. **Per-instance root on the host.** `…/retrobug/profiles/<appId>/<instanceId>/root/`, mode `0700`, owner = the app's UID, one per isolated environment, containing **no** bind-mounted or symlinked shared writable directory. The instance id is opaque and derived from (appId, instance name) — never from a guest-controlled string **[design rule]**.
2. **Root dirfd + component-at-a-time resolution.** Keep a long-lived `instance_root_fd` (`O_PATH|O_DIRECTORY|O_CLOEXEC`, verified against the expected `(st_dev, st_ino)` at creation and re-verified at entry). Resolution never touches host *strings*: each component is `openat(parent_fd, comp, O_PATH|O_NOFOLLOW|O_CLOEXEC)` + `fstat`. This is what makes `/proc/self/fd`-style tricks structurally impossible: there is no host path to leak into a guest-visible string.
3. **Per-instance mount table.** A trie of guest path → `{ backend, host_fd, flags, generation }`:
   * `rw-instance` — the instance root or a subdir of it; exactly one writable backend per guest path;
   * `ro-shared` — guest `/system/etc`, APK contents (via the zip/asset fd), read-only resource surfaces; `O_RDONLY`, `MAP_PRIVATE` only;
   * `virtual` — `/proc`, `/sys`, `/dev`, RetroBug's own compatibility surfaces, served from monitor memory;
   * `tmp` — guest `/data/local/tmp`, `TMPDIR`, inside the instance root, so "fully isolated filesystem" is verifiable.
   Longest-prefix wins; nesting is legal; teardown asserts that no backend fd is dropped while referenced.
4. **Host-fd capability table.** Guest fd (minus `FD_BASE`) indexes `entries[] = { host_fd, instance_id, guest_path_canonical, open_flags, refcount, generation, allowed_mmap_flags, dev, ino }`. Invariants: (a) every fd-using syscall requires `entry.instance_id == current_instance_id`; (b) identity re-verified from `(st_dev, st_ino)` on `mmap(MAP_SHARED)`, `link*`, `rename*`, `fchmod*`; (c) `generation` makes stale guest fds fail loudly instead of aliasing; (d) **RetroBug-internal fds live below `FD_BASE` and never appear in the table** — so "no dangling host paths / no ambient authority" is checkable by inspection: the table is the *only* source of host capabilities a guest can name.
5. **Resolver algorithm** — one function, no host strings: `resolve(start_entry_or_root_fd, path, follow_final, resolve_flags) → entry`
   * reject embedded NUL / over-long path; normalise repeated slashes;
   * start = absolute ? `instance_root_fd` : cwd entry's fd;
   * per component: `..` → if at root, stay (chroot semantics), else `openat(cur, "..")`; `.` → skip; else `O_PATH|O_NOFOLLOW` lookup + `fstat`;
   * on symlink with `follow`: re-root absolute targets at `instance_root_fd`, then expand **inside the trie** so mounts are honoured; if a symlink's target cannot be re-expressed as an in-instance guest path, fail. Budget `MAXSYMLINKS` overall plus a separate per-component budget;
   * honour `RESOLVE_BENEATH` (escape ⇒ `EXDEV`), `RESOLVE_NO_SYMLINKS` (⇒ `ELOOP`), `RESOLVE_NO_MAGICLINKS` (⇒ `ELOOP`), `RESOLVE_NO_XDEV` (⇒ `EXDEV`), `RESOLVE_IN_ROOT` (= the default algorithm above);
   * return an **entry**, never a string.
6. **`/proc` and `/sys` are monitor-served.** Guest-visible `/proc/self/{fd,fdinfo,cwd,root,mounts,mountinfo,status,stat,cmdline,environ}` synthesised from the capability table (guest fds, guest paths, guest root); `/proc/net/*` suppressed while the kill-switch is on. **[inference: this specific set is what guests commonly need; the leak risk for the host versions is established in §1.3]**
7. **Teardown** drains the capability table, closes the root dirfd and all backend fds, drops the mount table, then archives/removes the instance root. A non-empty table after exit is a leak **by definition** → assert in the exit path (test T-11).

**Why this beats `chroot`/mount-ns even where those exist:** those confine a *process*, and the confined subject still holds host capabilities it never needed (open fds, `/proc`, `socket`, `ptrace`). The capability-table design confines a *name space*, and the seccomp backstop (§2.6) removes the abilities names cannot express. Both together — plus Android's UID/SELinux boundary — are what make the product commitments verifiable rather than assumed.

## 2. OS-level Android primitives

Every verdict below answers the same three questions: can **an ordinary, user-installable, unprivileged app** use it; what does the kernel/SELinux *actually* enforce (as opposed to what the API implies); and what does it cost.

### 2.1 `android:isolatedService` / `android:isolatedProcess`

**What it is.** A `<service>` (or `<isolated-service>`) with `android:isolatedProcess="true"`: "If set to true, this service runs under a special process that is isolated from the rest of the system and has no permissions of its own. The only communication with it is through the Service API, with binding and starting." ([`<service>` manifest docs](https://developer.android.com/guide/topics/manifest/service-element); framework flag `ServiceInfo.FLAG_ISOLATED_PROCESS = 0x0002`, [`ServiceInfo.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/content/pm/ServiceInfo.java)).

**Usable by an ordinary app: YES** — no special permission is needed to *declare* or *bind* an isolated service belonging to your own package. It is the mechanism Android itself uses for WebView and media DRM renderers.

**UID.** An isolated process is **not** the app's UID: "An 'isolated app' is an APP with UID between AID_ISOLATED_START (99000) and AID_ISOLATED_END (99999)" ([`public/isolated_app.te`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/public/isolated_app.te) header). Framework side: `Process.FIRST_ISOLATED_UID = 99000`, `LAST_ISOLATED_UID = 99999`, plus a separate band for app-zygote-spawned isolated processes `FIRST_APP_ZYGOTE_ISOLATED_UID = 90000 … LAST = 98999` with `NUM_UIDS_PER_APP_ZYGOTE = 100` ([`Process.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/os/Process.java)). UIDs are allocated per process from a `IsolatedUidRange` / `IsolatedUidRangeAllocator` ([`ProcessList.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/am/ProcessList.java)), and **"If this is an isolated process, it can't re-use an existing process"** (`ProcessList.startProcessLocked`), i.e. **each bind gets its own process with its own UID** ([`ActiveServices.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/am/ActiveServices.java) comment: "each time we call startProcessLocked() we will get a new isolated process"). That is the one primitive in this list that gives **per-instance** isolation for free (§2.9).

**SELinux domain.** `isolated_app` (and the shared attribute `isolated_app_all`, plus the newer `isolated_compute_app`), declared via [`private/isolated_app.te`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/isolated_app.te):
```
typeattribute isolated_app coredomain;
app_domain(isolated_app)
isolated_app_domain(isolated_app)
```
`app_domain()` (`public/te_macros:242`) gives it the `appdomain` attribute; `isolated_app_domain()` (`public/te_macros:272`) gives `isolated_app_all`.

**Filesystem rights — close to none.** From [`private/isolated_app_all.te`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/isolated_app_all.te):
```
# Access already open app data files received over Binder or local socket IPC.
allow isolated_app_all { app_data_file privapp_data_file sdk_sandbox_data_file }:file
     { append read write getattr lock map };
...
# Isolated apps should not directly open app data files themselves.
neverallow isolated_app_all app_data_file_type:file open;
```
Note what is **missing** from that allow: `open`, `create`, and **any `dir` permission at all**. Combined with the neverallow, an isolated process cannot *name* a file — it can only consume file descriptors that somebody else opened and handed over Binder/IPC. Reinforcing this: `dontaudit isolated_app_all shell_data_file:dir search` (`/data/local/tmp`), `neverallow isolated_app_all cache_file:dir ~{ r_dir_perms }` ("Do not allow isolated_apps access to /cache"), and the external-storage block ("Do not allow isolated_app_all to access external storage, except for files passed via file descriptors (b/32896414)"). The framework agrees: **"If it's an isolated process, it should not even mount its own app data directories, since it has no access to them anyway"** (`ProcessList.java`, in the bind-mount setup).
*Exception that matters to RetroBug:* the installed APK's label is `apk_data_file`, and `public/file.te:381` shows it is **not** in `app_data_file_type` (`type apk_data_file, file_type, data_file_type, core_data_file_type;`). `private/app.te:442-443` grants appdomain `apk_data_file:dir { open getattr read search ioctl lock }` and `apk_data_file:file { getattr open read ioctl lock map x_file_perms }` (where `x_file_perms = { getattr execute execute_no_trans map }`, [`public/global_macros:24`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/public/global_macros)). **So an isolated service can open, read, mmap — even `execute_no_trans` from — its own APK.** Guest code inside the APK is reachable; guest *writable storage* is not, except through brokered fds.
*`dalvikcache_data_file`* (the AOT/oat store) is likewise not `app_data_file_type` and appdomain gets `r_file_perms` + `execute` (`private/app.te:207-208, 434`).

**Network rights — none, by neverallow.** `private/isolated_app_all.te`:
```
# No creation of sockets families other than AF_UNIX sockets.
# List taken from system/sepolicy/public/global_macros - socket_class_set
# excluding unix_stream_socket and unix_dgram_socket.
neverallow isolated_app_all { self ephemeral_app priv_app sdk_sandbox_all untrusted_app_all }:{
  socket tcp_socket udp_socket rawip_socket netlink_socket packet_socket … icmp_socket …
} create;
```
and the positive rule in `private/isolated_app.te` with its comment:
```
# Allow access to network sockets received over IPC. New socket creation is not permitted.
allow isolated_app { ephemeral_app priv_app untrusted_app_all }:{ tcp_socket udp_socket } { rw_socket_perms_no_ioctl };
```
**This is the strongest network kill-switch available to an unprivileged app, and it is kernel/SELinux-enforced rather than app-polite**: inside an isolated process, RetroBug does not need to trust its own syscall filter for `socket(AF_INET,…)` — the kernel refuses it. It also closes the `getaddrinfo`→`dnsproxyd` hole for *data* (AF_UNIX to netd may still be reachable — see §2.7(e) — so DNS text can still leak even without an Internet path; verify with T-08).

**Binder / callbacks / fds.** Isolated processes talk to the system only through the binding client, and service lookups are hard-limited:
```
# b/17487348
# Isolated apps can only access three services,
# activity_service, display_service, webviewupdate_service.
neverallow { isolated_app_all -isolated_compute_app } { service_manager_type
    -activity_service -display_service -webviewupdate_service }:service_manager find;
neverallow isolated_app_all vndbinder_device:chr_file *;
neverallow { isolated_app_all -isolated_compute_app } hwbinder_device:chr_file *;
```
So: **yes**, it can hold Binder callbacks to its host app (that is the only channel, and `allow isolated_app_all app_zygote:fd use` / `webview_zygote:fd use` show the inheritance path), and **yes**, it can receive fds — indeed file *and* socket access is designed around received fds. It cannot `find` Audio/Window/Connectivity/etc., so every Android runtime call the guest makes that needs another system service must be proxied by the host process. **Graphics driver access is denied**: `neverallow { isolated_app_all -isolated_compute_app } gpu_device:chr_file { rw_file_perms execute };` (contrast `private/app.te:393` which grants `{ appdomain -isolated_app_all } gpu_device:chr_file rw_file_perms`). RetroBug's GL/audio surface therefore must run in the host process and ship pixels/samples to the sandbox over Binder — a real cost, and a strong argument for keeping *graphics* out of the sandbox (§2.9, §Recommended design).

**How many may a manifest declare?** No AOSP-wide cap on *declarations* was found; the practical ceiling is the UID pool: the global isolated band is 99000-99999 (1000 uids, device-wide, shared with every other app's isolated services), and each app zygote gets a range of `NUM_UIDS_PER_APP_ZYGOTE = 100` from 90000-98999 ([`Process.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/os/Process.java), `ProcessList.IsolatedUidRangeAllocator` — allocation returns −1 when the range is exhausted). **[inference]** RetroBug should therefore size the number of *simultaneously running* isolated environments conservatively (≤ a handful per app) rather than assume 100.

**Memory/CPU limits.** No hard per-isolated-process memory ceiling was found in AOSP. What exists is *priority*: bound isolated processes get "slightly worse score than their client" (`OomAdjuster.java:2953`), and they are killed as soon as they stop being needed — `app.killLocked("isolated not needed", …, ApplicationExitInfo.SUBREASON_ISOLATED_NOT_NEEDED, true)` (`OomAdjuster.java:1453-1465`). Consequences for RetroBug: an isolated environment is **not** a long-lived daemon; it can be reaped when the user backgrounds the app, so lifecycle must be "recreate on entry" and profile state must be durable on disk (in the host-brokered instance root), never process-resident-only.

**Verdict.** The single most valuable OS primitive for RetroBug's optional environment: distinct UID per instance, no filesystem naming, no socket creation, 3 allowed service lookups — all *neverallow*-enforced, i.e. OEMs cannot accidentally widen it without violating CTS/SELinux build-time checks. Its price is that RetroBug's host process becomes a mandatory broker (fds in, services proxied, GPU kept host-side).

### 2.2 `isolated_app` and `execmem` — the make-or-break question

**Verdict: YES — an isolated process may allocate executable anonymous memory, so RetroBug's dynamic translator can JIT there.**

Evidence chain:
1. `allow appdomain self:process execmem;` with the comment `# WebView and other application-specific JIT compilers` — [`private/app.te:189`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/app.te).
2. `isolated_app` **is** appdomain: `app_domain(isolated_app)` → `typeattribute $1 appdomain;` ([`public/te_macros:242-243`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/public/te_macros)).
3. No neverallow removes it. Grepping the whole `main` tree (archive download, 2026-09) for `execmem` yields allows for `appdomain`, `app_zygote`, `webview_zygote`, `zygote`, `hal_drm`, `system_server_startup`, plus neverallows only for `perfetto`, `traced`, `traced_probes`, a conditional one on `system_server`, and `microdroid/system/private/domain.te:271: neverallow * self:process { execmem execheap execstack };` — **microdroid (pVM guests), not Android apps**.
4. What *is* universally forbidden: `neverallow * self:process { execstack execheap };` ([`private/domain.te:1342`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/domain.te)), with the comment "We would also like to minimize execmem but it seems to be required by some device-specific service domains." → RetroBug may `mmap(PROT_EXEC)` anonymous pages but may **not** make its stack or `malloc` heap executable.
5. File-backed exec from the *writable* data dir is forbidden, and isolated apps are named explicitly in that neverallow:
```
# Sensitive app domains are not allowed to execute from /data
# to prevent persistence attacks and ensure all code is executed from read-only locations.
neverallow { bluetooth isolated_app_all nfc radio shared_relro sdk_sandbox_all system_app } {
  data_file_type -apex_art_data_file -dalvikcache_data_file -system_data_file # shared libs in apks
  -apk_data_file }:file no_x_file_perms;
```
([`private/app.te`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/app.te), fetched 2026-09) → so: no executing a JIT cache written into the instance directory, but executing/mapping out of the **APK** and **dalvik-cache** remains allowed (the exclusions).
6. The memfd/tmpfs route is explicitly provisioned. `app_domain()` contains `type_transition $1 tmpfs:file appdomain_tmpfs;` **and** `allow $1 appdomain_tmpfs:file { execute getattr map read write ioctl };` (`public/te_macros:245-247`) — an app's own tmpfs/memfd objects are executable *for that domain*. AOSP even states the purpose in the app-zygote policy: `# Allow exec mapping from tmpfs (memfds) for binary translation` → `allow app_zygote app_zygote_tmpfs:file execute;` ([`private/app_zygote.te`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/app_zygote.te)).

**Consequences for RetroBug, in priority order** (consistent with [doc 09](09-android-executable-memory-jit-permissions.md)):
* Primary: anonymous `mmap(PROT_READ|PROT_WRITE|PROT_EXEC)` arenas (permitted by `self:process execmem`), or the memfd dual-view trick (W on the memfd fd, X on a second mapping) which additionally gets `appdomain_tmpfs`/`app_zygote_tmpfs` execute.
* The "write translated code to a file in the instance dir, then mmap it executable" design is **closed** — both by the `/data`-exec neverallow above and by `neverallow { all_untrusted_apps … } { app_data_file privapp_data_file }:file execute_no_trans` ([`private/app_neverallows.te`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/app_neverallows.te)). A translated-code cache must therefore be either (a) re-derived at entry, (b) stored as data and *loaded* into an anonymous RWX arena, or (c) executed out of the APK/`apk_data_file` — which an **offline, package-time** translator can write to only if the artifact ships inside the APK, so (b) is the realistic option. **[inference from the rules above]**
* Isolated processes are forked from the **app zygote** when `useAppZygote` is set (`ServiceInfo.FLAG_USE_APP_ZYGOTE = 0x0008`: "the service (which must be isolated) will be spawned from an Application Zygote, instead of the regular Zygote… call a static callback into the application to allow it to perform application-specific preloads (such as loading a shared library)… measure memory usage"), which is exactly the "pre-warm the translator + load the guest `.so`s once, fork per instance" pattern. Caveats quoted in the same javadoc: an extra resident process, and memory behaviour depends on how many isolated services share it. The app zygote is also where the *setuid-to-isolated-range* seccomp filter lives: "Set the UID/GID of the process. **This will be further limited to a range of isolated UIDs with seccomp.**" + `allow app_zygote isolated_app:process dyntransition;` (`private/app_zygote.te`, implemented by `install_setuidgid_seccomp_filter()` in [`bionic/libc/seccomp/seccomp_policy.cpp`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/seccomp/seccomp_policy.cpp)).

### 2.3 `android:process=":slotN"` — pre-declared sandbox processes

**Same UID. This is the decisive fact, and it means `:slotN` provides *no* per-instance isolation.**

* All processes of one package — however many `android:process` names it declares — run as the **same app UID**; only isolated services get the 99000+/90000+ band (§2.1). (Android's security model: one UID per app, all its processes and files under it — [Android security model](https://source.android.com/docs/security/features/sandbox).)
* **Filesystem:** sibling processes own each other's files by DAC (same uid ⇒ `0700` is irrelevant), and the SELinux type is identical (`untrusted_app`), so `allow appdomain app_data_file:file create_file_perms` covers both. Nothing separates slot1's instance root from slot2's.
* **SELinux neverallows do not help between same-type processes.** `app_domain()` contains `neverallow { appdomain -runas_app -shell -simpleperf -$1 } $1:file no_rw_file_perms;` — the `-$1` exception is there precisely because a process must be able to touch *its own* files, so it excludes same-type access from the prohibition (`public/te_macros:249-250`).
* **ptrace / `/proc/PID/mem`:** `allow untrusted_app_all self:process ptrace;` exists — "gdbserver for ndk-gdb ptrace attaches to app process" ([`private/untrusted_app_all.te:102-103`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/untrusted_app_all.te)), and `allow isolated_app_all self:process ptrace;` for Breakpad. `self:` is **type**-scoped, not process-scoped, so within one UID it does not forbid a sibling attach; the remaining gates are the kernel's `ptrace_may_access()` (passes for same-UID) and Yama `ptrace_scope`. `CONFIG_SECURITY_YAMA` is **absent from the GKI `gki_defconfig`** for android13/14/15 ([`arch/arm64/configs/gki_defconfig`](https://android.googlesource.com/kernel/common/+/refs/heads/android15-6.6/arch/arm64/configs/gki_defconfig)), and `init.rc` does not set `kernel.yama.ptrace_scope` ([`system/core/rootdir/init.rc`](https://android.googlesource.com/platform/system/core/+/refs/heads/main/rootdir/init.rc)) — so on GKI builds there is **no Yama gate** **[inference from absence of both config and sysctl; must be verified on device, T-04]**. Cross-*app* ptrace is nevertheless blocked: `neverallow { domain -$1 -crash_dump -runas_app -shell -simpleperf } $1:process ptrace;` plus `neverallow appdomain { domain -appdomain }:process ptrace;` (`private/app.te:562`) and `neverallow { domain -vold -dumpstate … } self:global_capability_class_set sys_ptrace;` (`private/domain.te:1613-1625`).
* **What `:slotN` *is* good for:** a separate address space and a separate lifecycle (its own ART heap, its own process-kill blast radius, no shared globals with the main process), plus `allow appdomain appdomain:fifo_file rw_file_perms` and `allow appdomain appdomain:unix_stream_socket { getopt getattr read write shutdown }` (`private/app.te:243,416`) make same-app IPC first-class. That is convenient for stability, and it is the natural host for RetroBug's **monitor** when the guest must not see monitor state — but it must never be described to users as an isolation boundary.
* **Verdict.** Use `:slotN` for *reliability* and for placing the monitor outside the guest's thread set; use isolated services (§2.1) when the product promises isolation. Every UID-scoped shared resource (kernel keyring, System V IPC, POSIX MQ, the app's `files/` tree, `SharedPreferences`, and per-app `Settings.System`/`Secure` keys) is a channel between slots by construction (§2.9).

### 2.4 Unprivileged user namespaces (`CLONE_NEWUSER` / `unshare`)

**Verdict: not usable by an app on Android.**

* **SELinux: the object class exists and nobody is granted it.** `private/access_vectors` defines `class user_namespace { create }` and `private/security_classes` lists `user_namespace`, but a tree-wide grep of the `main` sepolicy archive (excluding `prebuilts/` and `microdroid/`) for `user_namespace` in any `.te`/`.cil`/macro file returns **zero rules**. SELinux is default-deny, so `unshare(CLONE_NEWUSER)` from `appdomain` (or any platform domain) is refused **[inference from the absence of any allow rule; verify on device, T-05]**.
* **Kernel config: `CONFIG_USER_NS` is off by default and absent from GKI.** `init/Kconfig`: `config USER_NS / bool "User namespace" / default n` ([source](https://raw.githubusercontent.com/torvalds/linux/master/init/Kconfig)); the symbol does not appear in `gki_defconfig` for android13-5.10, android14-5.15 or android15-6.6, and those files *do* spell out namespace choices (`CONFIG_NAMESPACES=y`, `# CONFIG_PID_NS is not set`) ([`gki_defconfig`](https://android.googlesource.com/kernel/common/+/refs/heads/android15-6.6/arch/arm64/configs/gki_defconfig)). `user.max_user_namespaces` is not written by `init.rc` **[checked 2026-09]**.
* **seccomp is not the blocker:** `unshare(int)` and `setns(int, int)` **are** in bionic's `SYSCALLS.TXT` (lines 326-327) and appear in no blocklist, so the app filter permits the *call*; the denial is SELinux/capability-level. Apps also lack the capabilities namespaces would need: `neverallow ~dac_override_allowed self:global_capability_class_set dac_override;` and the `sys_ptrace` neverallow above show Android keeps app capability sets empty (`private/domain.te`).
* **Why it wouldn't have helped anyway:** a user namespace does not grant access to files the process could not already open; it grants a private `CAP_SYS_ADMIN` *inside* the namespace, which is exactly the amplifier RetroBug must not hand to untrusted guest code (idmapped mounts, fuse-style re-views, `setns` games). Denying it costs RetroBug nothing, because §1.5's VFS needs no kernel namespacing.
* Even where a vendor build does enable it, **do not build the sandbox on it**: RetroBug cannot verify the config across the fleet, and the product commitment is verification, not assumption.

### 2.5 Mount namespaces / `pivot_root` / `chroot` / `umount2`

**Verdict: all four are closed to an app, by three independent layers.**

1. **SELinux, app-wide:** `# Ability to perform any filesystem operation other than statfs(2). # i.e. no mount(2), unmount(2), etc.` followed by `neverallow appdomain fs_type:filesystem ~getattr;` ([`private/app.te:667-669`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/app.te)); and the mount allowlist neverallow `neverallow { domain -apexd -dexopt_chroot_setup -init -kernel -otapreopt_chroot -recovery -update_engine -vold -zygote … } { fs_type -sdcard_type -fusefs_type }:filesystem { mount remount relabelfrom relabelto };` ([`private/domain.te:1985-2002`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/domain.te)). `appdomain` is not in that list.
2. **seccomp, app filter:** `SECCOMP_BLOCKLIST_APP.TXT` blocks, for `all` architectures, `chroot(const char*)`, `mount(...)`, `umount2(const char*, int)`, plus `acct`, `syslog`, `swapon/swapoff`, `sethostname`, `reboot`, `init_module`, `delete_module` ([`bionic/libc/SECCOMP_BLOCKLIST_APP.TXT`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/SECCOMP_BLOCKLIST_APP.TXT)).
3. **syscall-table reachability:** `pivot_root` is not in bionic's `SYSCALLS.TXT` at all (§1.4), so it is outside the generated allowlist.
4. **Capability inheritance note:** `neverallow appdomain app_zygote:capability { chown };` and the blocklist header comment "the seccomp filter must be installed while the process still has CAP_SYS_ADMIN; changing the uid would remove that capability" — i.e. an app process has **no** `CAP_SYS_ADMIN` after the UID change ([`SECCOMP_BLOCKLIST_APP.TXT`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/SECCOMP_BLOCKLIST_APP.TXT) comments; `neverallow` quoted in [`private/app_zygote.te`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/app_zygote.te)).

**Verdict for the design:** "chroot-like root" in §1.5 must be a *fiction maintained by the monitor*, not a `chroot(2)`. RetroBug's guest-visible root is a dirfd plus a resolver, and the correct guest return values for `chroot`/`pivot_root`/`chdir("..")` are emulated.

### 2.6 Self-installed seccomp-bpf filters (the kernel backstop)

**Verdict: usable, cheap, and required — but it is a *negative* filter only, and it can be installed only in a process RetroBug controls the birth of.**

* **Mechanism.** `seccomp(SECCOMP_SET_MODE_FILTER, flags, &prog)`; `prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog)` is the legacy form bionic itself uses: `// This assumes either the current process has CAP_SYS_ADMIN, or PR_SET_NO_NEW_PRIVS bit is set.` (`install_filter()` in [`bionic/libc/seccomp/seccomp_policy.cpp`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/seccomp/seccomp_policy.cpp)). The kernel agrees: `if (!task_no_new_privs(current) && !ns_capable_noaudit(current_user_ns(), CAP_SYS_ADMIN)) return -EACCES;` ([`kernel/seccomp.c`](https://raw.githubusercontent.com/torvalds/linux/master/kernel/seccomp.c), ~line 691). An app has no `CAP_SYS_ADMIN`, so **RetroBug must `prctl(PR_SET_NO_NEW_PRIVS, 1)` first** in the thread that will install the filter.
  Android does *not* set no-new-privs for apps: `SetUpSeccompFilter()` is called in the zygote child while it still has `CAP_SYS_ADMIN`, with the comment "Must be called when the new process still has CAP_SYS_ADMIN, in this case, before changing uid from 0, which clears capabilities. **The other alternative is to call prctl(PR_SET_NO_NEW_PRIVS, 1) afterward, but that breaks SELinux domain transition (b/71859146).**" ([`core/jni/com_android_internal_os_Zygote.cpp`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/jni/com_android_internal_os_Zygote.cpp), ~line 2005). **[inference]** RetroBug can set the bit itself *after* its domain transition has happened — but this must be proven on device (T-06), including whether it interferes with anything RetroBug needs later.
* **Filters are cumulative and inherited.** A process may add filters but never remove or relax one; filters survive `fork()` and `execve()`; `SECCOMP_FILTER_FLAG_TSYNC` propagates a new filter to all threads of the process (needed here because RetroBug's guest is multi-threaded and a per-thread filter would leave a hole). The kernel evaluates all installed filters and the **most restrictive** action wins, so a later filter can downgrade a permitted call to `SECCOMP_RET_ERRNO`/`SECCOMP_RET_KILL` but can never restore a call the app baseline already denies — which is exactly why `openat2`/`landlock` cannot be recovered (§1.4).
* **Android's baseline is an allowlist of bionic's syscall set.** "Android O includes a single seccomp filter installed into zygote, the process from which all the Android applications are derived… The seccomp filter allows: all the syscalls exposed via bionic (the C runtime for Android). These are defined in `bionic/libc/SYSCALLS.TXT`… In Android O, the system crashes an app that uses an illegal syscall… `signal 31 (SIGSYS), code 1 (SYS_SECCOMP)`" ([Seccomp filter in Android O](https://android-developers.googleblog.com/2017/07/seccomp-filter-in-android-o.html)); the filter is generated by [`genseccomp.py`](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/tools/genseccomp.py) from `SYSCALLS.TXT ± SECCOMP_{ALLOW,BLOCK}LIST_{COMMON,APP}.TXT`, and a second filter for the compat architecture is chained in (`secondary_app_filter = arm_app_filter` in `seccomp_policy.cpp` — i.e. an arm64 app process also carries the 32-bit ARM policy). Practical consequence for RetroBug: **guest code can never reach a syscall that bionic does not implement**, which silently invalidates several classic escapes (`openat2`, `io_uring_*`, `landlock_*`, `pivot_root`, `keyctl`) — and it means RetroBug's *own* host-side syscall usage must stay inside the same set.
* **What RetroBug's filter should deny in the sandbox process** (all confirmed reachable-by-default because they are in `SYSCALLS.TXT`): `execve`, `ptrace`/`process_vm_readv`/`process_vm_writev`/`pidfd_getfd`/`pidfd_open`, `unshare`/`setns`, `setxid` variants already blocked, `socket` (or `socket` with `args[0] ∈ {AF_INET, AF_INET6, AX25, …}` → `ERRNO(EACCES)` while keeping `AF_UNIX` for dnsproxyd/binder), `connect`/`bind`/`sendto`/`sendmsg` (defence in depth behind the monitor), `perf_event_open`, `userfaultfd`, `bpf`, `kcmp`, `reboot`-adjacent extras, and `ioctl` on non-whitelisted fds (note: seccomp-bpf cannot see ioctl *command* vs fd identity well enough — BPF sees only raw args, so the ioctls must be brokered by the monitor rather than filtered).
* **Limits to state honestly.** (a) A filter cannot distinguish "this `write(fd, …)` is for the guest" from "this `write()` is RetroBug's own" — argument-based filtering sees numbers only, so the filter must apply to a **process that contains no trusted RetroBug code**. In the *normal* in-process path, RetroBug cannot seccomp itself without breaking its own host syscalls; that is why §Recommended design puts the isolated environment in a separate process. (b) seccomp cannot block anything that isn't a syscall — `__system_property_read` (no syscall), already-`mmap`'d shared memory, or `dlopen`'d host libraries that make syscalls on the guest's behalf (§1.1). (c) `SECCOMP_FILTER_FLAG_NEW_LISTENER` (user notification) requires `CAP_SYS_ADMIN`, so RetroBug cannot implement a "trap-to-userspace" filter without a privileged helper **[inference: no app-side grant of `SECCOMP_USER_NOTIF` permission exists; T-06 confirms empirically]**. (d) On Android 14+/16 some OEM builds add their own filters; a filter RetroBug installs at init time is fine, but OEM variance means the *baseline* set of blocked syscalls is not identical across devices (doc 09 reaches the same conclusion for `execmem`).

### 2.7 Network kill-switch — the five candidate routes

**(a) `VpnService` as a per-UID firewall (what NetGuard / Firewall No Root do).**
Available to an ordinary app (declares a service with `android:permission="android.permission.BIND_VPN_SERVICE"` + the `android.net.VpnService` intent filter). AOSP's own javadoc enumerates the constraints: "**User action is required the first time an application creates a VPN connection**", "**There can be only one VPN connection running at the same time.** The existing interface is deactivated when a new one is created", "A system-managed notification is shown during the lifetime of a VPN connection", "The network is restored automatically when the file descriptor is closed… covers the cases when a VPN application is crashed or killed by the system", and "`prepare` … the right can be revoked at any time" ([`frameworks/base/core/java/android/net/VpnService.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/net/VpnService.java)). Per-UID scoping is explicit: `Builder.addAllowedApplication()` — "**If this method is called at least once, only applications added through this method (and no others) are allowed access. Else … all applications are allowed by default. If some applications are added, other, un-added applications will use networking as if the VPN wasn't running**", and "A Builder may have only a set of allowed applications OR a set of disallowed ones, but not both" (same file). Note there is **no** `addAllApplications()` API — the "all apps" case is simply *not calling* the allow/disallow methods.
*How the firewall pattern works:* establish a tunnel that offers no route/no proxy (or drops every packet), `addAllowedApplication(<every package except the ones opted in>)` so only opted-in UIDs enter the tunnel and then die there. Cost/UX caveats, all documented above: it is **device-global and exclusive** (it evicts the user's own VPN; the user's VPN evicts it), it needs a visible system notification and a consent dialog each first run, it is torn down when the process dies (network "restored automatically"), and the OS gives no way to make it non-negotiable. It also cannot enforce anything on RetroBug's *own* UID, so for RetroBug it can only implement "the whole app is offline", not "instance A offline while the host stays online" — and per-instance network policy inside one UID **must** come from the syscall layer (d) anyway.
*Why the alternatives for UID→socket mapping are closed:* "Apps may not read /proc/net/{tcp,tcp6,udp,udp6}. These files leak information across the application boundary. VPN apps may use the `ConnectivityManager.getConnectionOwnerUid()` API to perform UID lookups." → `neverallow { appdomain -shell } proc_net_tcp_udp:file *;`, and apps are excluded from `/proc/net` entirely by `r_dir_file({ appdomain -ephemeral_app -isolated_app_all … -untrusted_app_all }, proc_net_type)` ([`private/app.te:1-17, 714-717`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/app.te)); privileged netlink is blocked too: `neverallow { appdomain -network_stack } domain:{ netlink_tcpdiag_socket netlink_nflog_socket netlink_xfrm_socket netlink_audit_socket netlink_dnrt_socket } *;` (`private/app.te:538-545`). So **`netlink INET_DIAG` socket-to-UID enumeration is not available to an unprivileged app at all** — the mechanism some Linux firewalls use simply does not exist on Android, which is precisely why NetGuard-style apps must use a VPN.

**(b) `ConnectivityManager` / `NetworkCapabilities` per-request binding.** `NetworkRequest`/`bindProcessToNetwork`/`bindSocket` choose *which* network to use; they do not deny use of a network, and the binding is process-wide (one network per process), not per-guest-instance. Useful for "route this instance through cellular/never-roaming" and for detecting loss of connectivity; useless as a kill-switch. **[inference from the documented API semantics](https://developer.android.com/reference/android/net/ConnectivityManager).**

**(c) `setRestrictedBackgroundData` / AppOps.** The background-data restriction is a *system/user*-controlled setting (Settings → Data Saver, AppOps `OP_RESTRICT_BACKGROUND_DATA`); an ordinary app cannot set it for itself, cannot set it per-instance, and it only applies to *background* state, so it is neither enforceable nor sufficient. It is also not a hard boundary (restrictions are bypassed for foreground/whitelisted cases). **Verdict: not usable.** **[UNVERIFIED in this pass — no AOSP source read for the permission gate; see Open questions.]

**(d) Syscall-layer denial (the primary mechanism for guest code).**
Strongest available for guest code, because the guest has no way to reach the kernel except through the monitor: `socket()`, `connect()`, `bind()`, `sendto()`, `sendmsg()` return `EACCES`/`ENETUNREACH` unless that instance's profile says otherwise, and `AF_NETLINK`/`AF_PACKET`/`AF_BLUETOOTH`/`AF_VSOCK` etc. are never offered at all. This also lets the policy be **per-instance** (the monitor knows which instance is calling), which no OS mechanism above can do inside one UID.
*The soundness condition:* the guest's network can only be as closed as the set of host paths RetroBug exposes. Every shim that can produce network effects must be audited and routed through the same gate — `socket`/`connect`, but also `getaddrinfo` (→ `dnsproxyd` AF_UNIX socket to netd: `/dev/socket/dnsproxyd u:object_r:dnsproxyd_socket:s0`, [`private/file_contexts:161`](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/file_contexts)), `ConnectivityManager`/`NetworkAgent` JNI shims, `TrafficStats`, `libcutils` property reads that reveal network state, `SurfaceControl`/`mediaserver` paths that open sockets on the client's behalf, `WebView`/`cronet` (if the guest's DEX can instantiate a `WebView`, that is a full network stack the syscall layer never sees), and `JobScheduler`/`DownloadManager` (system-side fetches on the app's behalf). **Recommendation:** treat "network OFF" as a *policy object* consumed by the syscall monitor **and** by every shim, and enumerate the shim set in a checklist that CI diffs (see test T-07).
*Kernel help available:* if the instance runs in an **isolated process**, SELinux already denies socket creation outright (§2.1) — the monitor's gate becomes a UX nicety on top of a hard rule.

**(e) DNS leak routes.** Three distinct ones, and only the first is a syscall:
1. `getaddrinfo()` in the guest's emulated libc → monitor denies (or virtualises: serve from a per-instance hosts table).
2. `getaddrinfo()` in **host** code reached through a shim (JNI, `libandroid`, a guest-loaded `WebView`) → the host asks **netd**, so the query goes out with the *device's* DNS configuration and the app's UID; the monitor never sees a DNS packet. Blocking `AF_INET` in the shim is not enough if the shim still calls host resolver APIs: **host-side resolver calls must be part of the same policy object** (§1.1, item 2).
3. `__system_property_read` of `net.dns*` / `net.<iface>.dns*` and reads of `/proc/net/pnp`, `/proc/net/tcp*`, `/vendor/etc/resolv.conf`-like files: property reads issue **no syscall per lookup** (the region is `mmap`'d once), so a syscall-layer filter cannot catch them; the guest-visible `/proc` and property namespace must be *synthesised* (§1.5 item 6) and the shim layer must refuse `net.dns*`. Note the AOSP `neverallow { appdomain -shell } proc_net_tcp_udp:file *;` means RetroBug itself cannot even use `/proc/net` to audit what it has leaked — so the audit has to come from RetroBug's own logs.
Also worth noting: even inside an isolated process, `AF_UNIX` sockets are permitted, and `dnsproxyd` is an `AF_UNIX` socket, so **an isolated process may still resolve names** unless the monitor blocks the path **[inference from `isolated_app_all` neverallow scoping to non-AF_UNIX families; T-08 verifies]**.

### 2.8 Per-instance config/settings isolation

* **Android's own per-app storage split is coarse.** `Context.createDeviceProtectedStorageContext()` moves an app's storage from credential-encrypted to device-encrypted (`core/java/android/content/Context.java`) — it is a *different directory for the same UID*, not a sandbox. Both the CE and DE trees remain reachable by every process of the app (same UID, same SELinux type). `SharedPreferences` are per-`Context`; the framework explicitly warns against cross-process sharing of them: "**MODE_MULTI_PROCESS does not work reliably in some versions of Android, and furthermore does not provide any mechanism for reconciling concurrent modifications across processes. Applications should not attempt to use it. Instead, they should use an explicit cross-process data management approach such as ContentProvider**" ([`Context.java:264-272`](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/content/Context.java)). So Android offers no primitive for "two profiles of the same app" — **config isolation is necessarily RetroBug's own layer**.
* **Making "no global fallback" structurally provable.** The failure mode in every prior design is a lookup that silently falls through to a default: `get(key)` → app prefs → global prefs → hardcoded default. Make it a *closed* lookup with a mandatory namespace:
  1. One store per instance: `ProfileStore(instanceId)` where `instanceId = (appId, instanceName)` is a value that **must** be supplied by the caller — no constructor takes one argument. The key type is `NamespacedKey{ int instanceId; string domain; string name }`; the store's public API has no method accepting an un-namespaced key, so a "global" read is not expressible in the type system. **[design rule]**
  2. Reject the ambient path: the store must not read `SharedPreferences`, `Settings.System/Secure/Global`, system properties, or files outside the instance root *even for defaults*. Defaults live in a versioned table compiled into RetroBug keyed by `(guestPackage, configName)` — an explicit, auditable artifact, not an ambient lookup.
  3. Two-level separation only where the product needs it: *host* preferences (RetroBug's own UI settings) and *guest-visible* config (what the emulated Android reports to guest code) are different stores with different backends; a guest must never be able to read the host store and vice versa; the *normal* path's config lives in the normal path's namespace so an isolated profile can never be "inherited" by accident.
  4. Persistence inside the instance root (never in the shared prefs file), so that the FS guarantee (§2.1/§1.5) *is* the config guarantee: an isolated environment whose config directory is a subdir of its own root inherits its isolation for free.
  5. Verifiability: log/emit the resolved `(instanceId, key) → store` decision for every read during the leak-probe suite, and unit-test "with no profile created, the lookup *fails* rather than returning a default" — that is the property the product sells.
* **`Settings.System`/`Secure` are per-app-ID in a global table** (keyed by package name) — so two RetroBug instances serving the same guest package share those keys by construction unless RetroBug virtualises them. Guest reads of `Settings.*` go through RetroBug's shim anyway (the guest's `ContentResolver` query would be a host call), which is where the namespacing must be applied. **[inference; the guest-side plumbing is doc 02's scope]**

### 2.9 Cross-instance isolation: where the OS helps and where we only help ourselves

| Channel between two RetroBug guest environments | Does the OS separate it? | Who must enforce |
|---|---|---|
| `/data/data/<retrobug>` file tree | **No** for same-UID processes (`:slotN`, or threads in one process): same owner, same SELinux type | RetroBug VFS + capability table (§1.5) |
| … between one instance in an **isolated process** and the host | **Yes**, mostly: `neverallow isolated_app_all app_data_file_type:file open`, no dir perms, no app-data bind mounts — the sandbox only holds fds the host chose to hand it | OS + the host's fd-broking discipline |
| UID-scoped kernel state: keyring, SysV `shm`/`msg`/`sem`, POSIX MQ, `/proc/net` | **No** (all same-UID); `isolated_app_all` can't even create the non-AF_UNIX sockets, and apps can't read `/proc/net` | deny in guest ABI; isolated process for hard denial |
| `/dev/__properties__` (system properties, `net.dns*`, `ro.*`) | **No** — mapped once, read without syscalls; `get_prop(appdomain, …)` is granted per-property by policy | monitor must virtualise property reads; never forward to the real region |
| `ptrace` / `/proc/PID/mem` of a sibling slot | **Not reliably** — `allow untrusted_app_all self:process ptrace` (for ndk-gdb) + same UID; Yama appears absent from GKI | do not place two instances in same-UID processes; isolated processes have distinct UIDs |
| Host filesystem visible through a leaked path string (`/proc/self/fd`, error messages, `getcwd`) | **No** | resolver + synthetic `/proc` (§1.5) |
| Binder callbacks / system services proxied by the host | Only for isolated processes (3 services) | the shim allowlist |
| Network | **Yes** in an isolated process (neverallow), **No** for same-UID processes | monitor gate + isolated process |
| Transient state in the shared CPU core / translator cache | **No** — the core is shared by design | per-instance code-cache keys; flush/replace on instance switch; no cross-instance cache lookup by guest PC alone **[inference: doc 01's DBT cache must be instance-tagged]** |

**The honest summary:** Android gives RetroBug exactly two things it cannot fake — (i) the **UID + SELinux domain boundary of an isolated process**, which is what turns "we promise not to" into "the kernel refuses", and (ii) the **app baseline seccomp allowlist**, which removes several escape syscalls from the table for everyone. Everything else — path resolution, fd authority, config namespacing, property and `/proc` virtualisation, network policy inside one UID — is RetroBug enforcing rules on itself, and must therefore be *tested* (§Verification test plan) rather than assumed.

## 3. iOS

The same three questions, asked of the second target platform: can an ordinary App Store app use it, what does the kernel *actually* enforce, and what does it cost. Sections §3.1–§3.4 establish that iOS's answer to each is structurally different from Android's — one container, one UID, no process creation, no obtainable per-instance identity — and §3.5 is the disclosure list the brief demands. The recurring term below is **backstop**: on Android a bug in RetroBug's own mediation is caught by a kernel rule; on iOS there is nothing behind the monitor.

### 3.1 App Sandbox: one container per installed app

**What iOS actually gives.** iOS's sandbox is *path-scoped and unconditional*, not identity-scoped. Apple's file-system guide states it plainly ([File System Programming Guide, "File System Overview"](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html), archived 2026-09):

> "For security purposes, an iOS app's interactions with the file system are limited to the directories inside the app's sandbox directory."
> "An app is generally prohibited from accessing or creating files outside its container directories."
> "**Because iOS apps always run in a sandbox**, the system assigns specific ACLs and permissions to files created by each app."
> "During installation of a new app, **the installer creates a number of container directories for the app** inside the sandbox directory. These container directories constitute the app's primary view of the file system."

The containers created *at install time* are: a **bundle container** (the `.app`, read-only — "You cannot write to this directory… Writing to this directory changes the signature and prevents your app from launching") and a **data container** with `Documents/`, `Library/` (incl. `Library/Caches/`) and `tmp/`. The same table states the durability rules that matter to us: `Documents/` is "backed up by iTunes and iCloud"; `Library/Caches/` is **not** backed up and "if your app is not running and the device needs more disk space, the system can purge this directory"; `tmp/` is not backed up and "the system may purge this directory while your app is not running".

**RetroBug-iOS is ONE app.** That is the whole problem in one sentence. Every emulated guest instance — the normal path and every "isolated environment" — lives inside a single data container granted to a single installed bundle, because iOS creates containers *per installed app*, not per runtime subsystem. Android, by contrast, hands RetroBug a *second identity* for each isolated environment (§2.1: a fresh UID from the 99000–99999 / 90000–98999 pools, a distinct SELinux type, `neverallow isolated_app_all app_data_file_type:file open`). iOS has no analogue of either half of that.

**No per-app UID, therefore no per-instance UID.** Published platform research states the model explicitly: "All third party applications on iOS run within a sandbox… **While applications all run as the 'mobile' operating system user, they are contained within a unique directory… separation is maintained by the XNU Sandbox kernel extension**" ([MDSec, *Introduction to iOS Platform Security*](https://www.mdsec.co.uk/2012/05/introduction-to-ios-platform-security/)). iOS therefore has **no multi-user concept** (there is no second "user 0" per app, no `AID_ISOLATED_START` band, no per-app SELinux domain), and — the corollary that matters most for §2.9's table — **UID-scoped kernel objects are shared by construction across the whole device's app population**, not merely across instances: System V `shm`/`msg`/`sem`, POSIX shared memory, the `kqueue`/Mach send-right namespace reachable within the session, and file DAC ownership (`0700` means nothing when everyone is `mobile`). Whether Apple additionally layers per-app *MAC* labels over every one of those object classes is not documented in Apple's public developer docs; I could not verify the per-class behaviour in this pass, so it is **T-20** in the test plan (attempt `shm_open`/`shmget`/`semget` and a Mach port look-up from two apps I control).

**What iOS *does* give that is real, and where it stops.** Seatbelt path denial is genuinely kernel-enforced: a `open("/private/var/mobile/Containers/Data/Application/<someone-else>/…")` from RetroBug fails regardless of what RetroBug's code wants, and unlike Android's `isolated_app` case it does not depend on RetroBug choosing to be well-behaved. Two consequences, one good and one bad:

* **Good:** the *host-side* filesystem of iOS is small, closed and per-app. There is no `/sdcard`, no `/data/local/tmp`, no world-writable shared scratch, no MediaStore, and — because RetroBug ships all its native code in its own bundle and cannot `dlopen` from elsewhere (§3.4, [doc 04 §2.2](04-ios-feasibility.md)) — no code-loading surface outside the container. §1.3's "device nodes and shared paths" row has almost nothing to bite on.
* **Bad:** the OS boundary sits *outside* RetroBug, so it protects RetroBug from other apps and provides **zero** separation between RetroBug's own instances. Two guest instances are two directory subtrees inside one container, reachable by one process through one `open()`. There is no OS subject distinction to enforce against.

**The decisive implication for the design.** RetroBug-iOS must reuse the §1.5 monitor-side VFS as the **sole** enforcement layer. On Android the design has a backstop: if RetroBug's resolver is buggy, SELinux still refuses `isolated_app` the ability to *name* a file, and the kernel still refuses `socket(AF_INET)`. On iOS there is **no backstop equivalent to `isolated_app`**: a bug in the resolver is a bug in the isolation, full stop, because the process holding the bug already has DAC + MAC rights over the entire container. Three concrete design consequences:

1. **Instance roots are subdirectories of the data container, and that is a *convenience*, never a claim.** Layout: `Library/Application Support/RetroBug/profiles/<appId>/<instanceId>/root/` (§1.5 item 1 with the container as its parent). Do **not** put instance roots in `Documents/` — that directory is user-visible via Files and is iCloud/iTunes-backed, which breaks "fully isolated filesystem" for the guest's private data (a guest app's own database would be copied to iCloud and be readable by the user's other devices and by any backup extractor). Put roots under `Library/Application Support/`, and set `URLResourceValues.isExcludedFromBackup`/`isItemKeyProtectedByEncryption` per [Apple's data-protection guidance](https://developer.apple.com/documentation/uikit/protecting_the_user_s_data) **[inference on the exact API set; the backup-table citations above are the confirmed part — T-21]**.
2. **Never use App Groups as the instance boundary.** An App Group is a *sharing* primitive, documented as such: "Apps within an app group share access to a group container", and group membership additionally enables "interprocess communication (IPC) mechanisms such as Mach IPC, XPC, POSIX semaphores, shared memory, and UNIX domain sockets" ([`com.apple.security.application-groups`](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.application-groups), iOS 3.0+). Adopting one for convenience (e.g. to share an APK import) silently creates exactly the "shared mounts/cache/scratch" surface the product promises not to have, and it survives RetroBug's own code review because it is a *capability*, not a bug. Rule: **App Groups are allowed only for the import hand-off, and only into a staging path that the resolver treats as `ro-shared` and then copies out of** (§Recommended iOS design).
3. **Durability and purge semantics are part of isolation, not beside it.** Because the system may purge `tmp/` and `Library/Caches/` while the app is not running (quoted above) and because suspension kills all execution ([TN2277](https://developer.apple.com/library/archive/technotes/tn2277/_index.html), quoted in [doc 04 §5.4](04-ios-feasibility.md)), an isolated environment's *identity* (which instance, which profile, which network decision) must live in durable storage inside that instance's own root, and its translated-code/IR caches may live in purgeable storage but must be rebuildable. A design that stores the "network OFF" decision in `tmp/` is a design that silently re-defaults on the next launch.

**Verdict.** iOS's App Sandbox is a *single-tenant* guarantee. It gives RetroBug one container, one UID (shared with every other app), one seatbelt profile, and no OS-visible notion of "a second, isolated environment inside my app". Everything the product promises per instance — separate FS, network default, settings scoping, cross-instance invisibility — must be produced by the §1.5 VFS + capability table + §2.8 namespaced config store, running with no kernel help. This is exactly the configuration §1.1 warns about ("in-process mediation alone is *not* sound against a bug in the monitor"), with the Android backstop removed.

### 3.2 Extension processes as sandbox slots

**The question.** iOS *does* have a mechanism that produces "a second process, with its own container, running my own code": app extensions. If RetroBug could bind each isolated environment to an extension process, it would recover something like §2.1's structure. This section tests that idea and rejects it.

**What extensions really are — the confirmed part.** Apple's App Extension Programming Guide is explicit that the process and container are separate from the containing app ([*Extension Scenarios → Sharing Data with Your Containing App*](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html)):

> "**Even though an app extension bundle is nested within its containing app's bundle, the running app extension and containing app have no direct access to each other's containers.**"
> "An app extension's container is distinct from its containing app's container."
> "When you set up a shared container, the containing app—and each contained app extension that you allow to participate in data sharing—have **read and write access to the shared container**."
> "…the extension can complete the host app's request **and be terminated** without affecting the outcome of the task."
> "Recall that **other types of background tasks, such as supporting VoIP or playing background audio, are not available to app extensions.**"

So: separate address space ✔, separate container ✔, my own code ✔, and — unlike Android's isolated process — the extension *can* be given a container that the main app cannot read (unless an App Group is configured). That much is genuinely attractive.

**Why it cannot be RetroBug's slot mechanism — five independent blockers.**

1. **The containing app does not get to launch its own extension.** The documented entry point is *inbound*: `NSExtensionRequestHandling` is "**The interface an app extension uses to respond to a request from a host app**" ([Apple docs](https://developer.apple.com/documentation/foundation/nsextensionrequesthandling)) — the *host* is another app (or the system: Notification Center, Photos, Share Sheet), and the user drives it. I found **no** public API for "start N instances of my extension now, here is a work item" — the only app-driven families are the ones with domain-specific semantics: Network Extension providers via `NEVPNManager`/`NEFilterManager` (§3.3), WidgetKit reloads (system-scheduled), and push (`app-push-provider`). **[inference from the documented request model + absence of a launch API; T-23 searches the iOS 26 SDK for a containing-app-initiated extension launch.]** Android's `isolated-service` is precisely the opposite: *the app* binds, and "each time we call `startProcessLocked()` we will get a new isolated process" (§2.1). That control inversion is fatal for a "create/enter/run/exit/teardown" lifecycle: RetroBug cannot decide when the environment exists.
2. **Extension points are a closed, purpose-specific set, not a generic compute slot.** An extension must declare `NSExtensionPointIdentifier` + `NSExtensionPrincipalClass` for a point Apple recognises — e.g. `com.apple.networkextension.filter-data`, `com.apple.networkextension.app-proxy` ([NEFilterDataProvider](https://developer.apple.com/documentation/networkextension/nefilterdataprovider), [NEAppProxyProvider](https://developer.apple.com/documentation/networkextension/neappproxyprovider)). A "run this guest APK" extension point does not exist and cannot be requested. Inside a filter or proxy provider you have a *callback API about flows*, not a general runtime: the filter provider's own doc frames its contract as deciding whether to pass or block `NEFilterFlow` objects, and adds a privacy constraint that cuts against us — "the extension sandbox prevents the extension from moving network content outside of its address space" — i.e. it is deliberately unable to hand bytes to a UI process.
3. **Lifetime, budget and suspension.** Extensions are on-demand, short-lived, and killed after servicing a request (quoted above: terminated, with "background tasks… not available to app extensions"), while the emulator as a whole is suspended the moment the user leaves the app ("When the app is suspended, no code within the app's process runs", [TN2277](https://developer.apple.com/library/archive/technotes/tn2277/_index.html)). A guest that must run at 60 fps inside a foreground UI cannot live in a process the system may reap between requests, and there is no documented per-extension memory ceiling that I could retrieve from Apple's public docs (**[UNVERIFIED]** — the numbers float around WWDC material and vary by extension type and device; **T-22** measures the jetsam ceiling of each candidate extension type empirically by allocating until termination).
4. **Concurrency is not offered.** Even where an extension *is* running, nothing in Apple's documentation promises an app the ability to hold N simultaneous instances of the same extension; the request/response model is per-invocation and the system manages the process pool. **[inference from the documented model; T-22 attempts concurrent activations.]** RetroBug's product surface is "several independent environments, chosen by the user, one at a time or side by side" — it cannot be built on an undocumented concurrency allowance.
5. **Cost of data movement.** A slot must read the guest APK and its instance root. Because "the running app extension and containing app have no direct access to each other's containers" (quoted), the only ways in are (a) an App Group — which, per §3.1, *creates* the shared mount the commitment forbids — or (b) copying the whole APK + root into the extension's container per activation. (b) is O(guest size) per entry, which is fine for an image picker and useless for a running machine; and per-instance roots would need per-instance containers, i.e. one extension *target* (bundle id, Info.plist, embedded binary, review surface) per slot. N slots = N bundles, all carrying the same statically-linked core (§3.4).

**XPC services — the other candidate.** The `NSXPCConnection` class carries iOS availability in Apple's tables ("**iOS 6.0+**, iPadOS 6.0+, macOS 10.8+, Mac Catalyst 13.1+, tvOS 9.0+, watchOS 2.0+, visionOS 1.0+", described as "the primary means of creating and configuring the communication mechanism between two processes"), and the low-level `xpc` framework page is now listed for "iOS 17.4+" while describing the model as "**XPC services**… **The `launchd` system daemon manages these services, launching them on demand, shutting them down when idle, and restarting them if they crash**" ([XPC](https://developer.apple.com/documentation/xpc)). The transport is therefore present; the **peer is not obtainable**: an XPC service is a `launchd`-managed helper registered in a location a third-party iOS app cannot write (no `LaunchAgents`/`LaunchDaemons`, no install step), and iOS apps cannot spawn processes at all (§3.4). The practical consequence is that `NSXPCConnection` on iOS is used *by* the system to talk to *your* extension, not by you to mint helpers. **[inference from "launchd-managed" + "no process spawning on iOS" + the absence of any documented iOS XPC-service bundle layout for App Store apps; T-23 attempts to bundle and look up an XPC service from an iOS app and records the failure mode.]**

**Can one process read another's memory? (the `ptrace`/`task_for_pid`/`proc_pidfd` question).** Not for third-party apps, and the *reason* is worth stating precisely because it exposes how thin iOS's process model is for us:

* There is **no** `proc_pidfd`/`proc_pidfdinfo`/`kinfo_proc`-style procfs API on Darwin/iOS at all (that family is Linux-only; the iOS container has no `/proc`), so §1.3's `/proc/PID/*` attack surface simply does not exist on iOS — good news, and it removes a whole test class (§Verification test plan, T-24 asserts the guest's `/proc` cannot be back-ended by anything real).
* `ptrace(2)` on Darwin requires that "The process must… have the **same real UID as the tracing process**" unless the caller is the superuser ([Darwin `ptrace(2)`](https://keith.github.io/xcode-man-pages/ptrace.2.html); same page documents `PT_DENY_ATTACH`, which "sets a flag that denies future traces"). On iOS every app runs as `mobile` (§3.1), so that DAC condition is **satisfied for every other app** — the actual bar is elsewhere: AMFI/the code-signing monitor only lets a task be traced when the *target* is debuggable, i.e. dev-signed with `get-task-allow`. That is exactly the mechanism sideloaded JIT products exploit and exactly why they cannot ship ([doc 04 §1.2 and §2 row (c)](04-ios-feasibility.md): "the app runs under a debug attach (`get-task-allow` + `CS_DEBUGGED`-style permission), which is precisely why it cannot ship"). `task_for_pid()` inherits the same gate (the caller additionally needs debugger privileges, which are a Mac/Hardened-Runtime story). **[inference from the quoted docs + doc 04's cited evidence; I did not read the XNU policy function in this pass — T-24 verifies by having two of my own dev-signed/non-debuggable builds attempt `ptrace(PT_ATTACH)` and `task_for_pid()` on each other, expecting `EPERM`.]**
* Net effect: iOS *does* give cross-process memory invisibility, but RetroBug cannot *buy* it per instance, because the only available second processes are extension processes it cannot launch, feed, or keep alive.

**Verdict — state it plainly.** **iOS gives RetroBug NO OS-level per-instance process isolation.** There is no primitive, obtainable by an App Store app, that yields "one OS process with its own UID/container, launched and torn down at RetroBug's request, able to read only fds RetroBug hands it". Therefore **cross-instance isolation on iOS is enforced entirely in-process by RetroBug itself**: the §1.5 resolver, the §1.5 capability table, per-instance IR/code-cache tagging (§2.9 last row), and the §2.8 namespaced config store. What the OS guarantees is *inter-app* confidentiality (Seatbelt paths + per-app keybag + non-debuggability), which means an iOS isolated environment resists the **guest**, and resists **other apps**, but does **not** resist a defect in RetroBug — whereas on Android an `isolatedService`-backed environment resists the guest *even if RetroBug's resolver has a bug*. The product claim must be tiered accordingly: on Android the promise is "the kernel refuses"; on iOS it is "we refuse, and here is our test suite" (§3.5). **[design rule]** The two platforms must not share marketing wording, and the iOS UI copy should say *profile separation* / *per-instance private storage*, not *sandboxed process*.

### 3.3 Network Extension provider types and the approval burden

**The one OS-level network filter iOS offers third parties** is the Network Extension framework's *provider* family, and each provider is an app extension with its own principal class, extension point identifier, and entitlement value. The relevant types, from Apple's own docs:

| Provider | Extension point | What it can actually decide | Doc status |
|---|---|---|---|
| `NEFilterDataProvider` | `com.apple.networkextension.filter-data` | Per-flow pass/block on `handleNewFlow(_:)`, plus per-chunk decisions on `handleInboundData`/`handleOutboundData`; can show a block page for WebKit flows. iOS 9.0+. | [docs](https://developer.apple.com/documentation/networkextension/nefilterdataprovider) |
| `NEAppProxyProvider` | `com.apple.networkextension.app-proxy` | Receives each matching socket as an `NEAppProxyFlow` and must act as a transparent proxy (read/write the flow itself). `startProxy`/`stopProxy`/`handleNewFlow`. iOS 9.0+. | [docs](https://developer.apple.com/documentation/networkextension/neappproxyprovider) |
| `NETunnelProvider` | `com.apple.networkextension.packet-tunnel` | Owns a `utun` interface and all IP traffic through it; the "packet-oriented custom VPN protocol" of the framework overview. iOS 9.0+. | [docs](https://developer.apple.com/documentation/networkextension/netunnelprovider) |

The entitlement that gates all three is `com.apple.developer.networking.networkextension`, available **iOS 9.0+**, whose value is an array of provider strings — Apple lists exactly: `dns-proxy`, `app-proxy-provider`, `content-filter-provider`, `packet-tunnel-provider`, `dns-proxy-systemextension`, `app-proxy-provider-systemextension`, `content-filter-provider-systemextension`, `packet-tunnel-provider-systemextension`, `dns-settings`, `app-push-provider`, `relay`, `url-filter-provider` ([entitlement doc](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.networkextension)). The documented acquisition path is capability-based, not free-form:

> "To add this entitlement to an App Store app, **enable the Network Extensions capability in Xcode**. To add this entitlement to a macOS app distributed outside of the Mac App Store… **In the Certificates, Identifiers and Profiles section of the developer site, enable the Network Extension capability** for your Developer ID–signed app."

and, per-provider: "The `com.apple.developer.networking.networkextension` entitlement is required to use the `NEAppProxyProvider` class. **Enable this entitlement when creating an App ID in your developer account.**" ([NEAppProxyProvider](https://developer.apple.com/documentation/networkextension/neappproxyprovider))

**Approval burden — what is and isn't confirmed.** Confirmed: these keys are *capability-gated per App ID*, so they are not self-declarable the way `com.apple.security.cs.allow-jit` is on macOS; the framework overview warns that "some features have specific restrictions (for example, **some features only work on supervised iOS devices**)" ([Network Extension](https://developer.apple.com/documentation/networkextension)). The additional claim I came in to check — that `content-filter-provider` / `url-filter-provider` / the `*-systemextension` variants require an **Apple-approved use case** submitted as a special-entitlement request, and are not grantable to a general consumer app — I could **not** pin to a quotable Apple sentence in this pass. **[UNVERIFIED → Open questions item U-11, test T-26: on a throwaway App ID, attempt to enable each Network Extension capability value and record which are self-serve, which demand a request, and what the request form asks.]** Treat the burden as real but unquantified; the *practical* burden below is disqualifying on its own.

**Why none of them fits the commitment "network OFF by default, per-app explicit opt-in".** Three independent mismatches:

1. **Wrong scope, in the bad direction.** A provider is device-global and exclusive: it filters *all* flows on the device (or, for app-proxy, flows matched by a system-installed configuration), not "RetroBug instance #3". RetroBug's requirement is per-instance, which — exactly as §2.7(a) concluded for Android's `VpnService` ("There can be only one VPN connection running at the same time", and no ability to enforce on its own UID) — no OS mechanism can express. It also conflicts with the user's own VPN/security app, and is itself subject to the same eviction. **[inference from the documented single-active-provider/VPN model — confirm exclusivity, and whether a filter provider and a tunnel can coexist, in T-25.]**
2. **Wrong trigger and wrong lifetime.** Providers are extensions (§3.2): the system starts them, they must be *installed and enabled* (`NEVPNManager.saveToPreferences` + `startVPCTest`/user consent dialog; `NEFilterManager.isEnabled` is typically driven by a configuration profile in MDM deployments), they can be torn down by the user at any time, and RetroBug cannot assume the filter is active while the guest runs. A "network OFF" guarantee that depends on a user having approved and not later disabled a VPN-style configuration is not a default-off guarantee — it is opt-in protection, which inverts the commitment.
3. **Wrong direction of information.** For a *filter*, RetroBug would have to know which flows are the guest's, and the OS does not tell it (iOS has no per-UID flow attribution API exposed to a filter provider, unlike `ConnectivityManager.getConnectionOwnerUid()` on Android, §2.7(a)). And an app-proxy provider is the one type that *would* see guest traffic as flows — but taking those flows means RetroBug implements the transport, i.e. it becomes the network stack, with the entitlement burden of a VPN app and none of the isolation benefit.

**The DNS wrinkle, which reinforces the same conclusion.** Apple documents that an app proxy provider "receives DNS query flows (`NEAppProxyUDPFlow`) **only for apps using low-level DNS APIs** (e.g. `DNSServiceGetAddrInfo`)", while "Apps using high-level APIs (e.g. `URLSession`) do not generate separate DNS queries; the destination hostname is included in the `NEAppProxyFlow` endpoint information" ([NEAppProxyProvider](https://developer.apple.com/documentation/networkextension/neappproxyprovider)). That is iOS's version of §2.7(e): resolution is a system service reached through Mach/`mDNSResponder`, not a packet the app can be trusted to have refused. An NE provider is *not* a way to catch a resolver leak; refusing to call the resolver in the first place is.

**Verdict for RetroBug-iOS.** Do **not** build the isolated environment's network control on Network Extensions. The design is the §2.7(d) route only, made tighter because there is no kernel to fall back on:

* **Primary:** the monitor refuses `socket`/`connect`/`bind`/`sendto`/`sendmsg`/`shutdown`/`listen`/`accept` per instance (`EACCES` when OFF), and never offers `AF_NETLINK`/`AF_PACKET`/`AF_VSOCK`/`AF_BLUETOOTH` equivalents (Darwin has `AF_SYSTEM`/`PF_ROUTE`, which must be denied too — the guest's `route(4)` socket is a *configuration oracle* on iOS, so add it to the T-14 matrix).
* **Mandatory second half:** a **closed host-shim list** (§1.1 item 2, T-07 checklist) — on iOS the leak-shaped shims are `URLSession`/`CFNetwork`, `CNURLConnection`, `NWConnection`/Network framework, `DNSService*`, `NSNetService`/Bonjour, `MCSession`/GameKit, `WKWebView` (if the iOS build embeds WebKit for anything — it is a full network stack the monitor never sees, and in-process JSC has no JIT but *does* have sockets), plus CloudKit and `AVAssetDownload`. If a shim is not on the list, it may not exist in the binary; CI enforces it by symbol-scanning the linked image (§Verification test plan, T-27).
* **Optional, clearly-labelled user extra:** a "device-wide offline while RetroBug is foregrounded" toggle implemented as a *suggestion* (Settings → tell the user to enable their own VPN/airplane mode) rather than a shipped `NETunnelProvider`; v1 should ship no NE provider at all. Rationale: entitlement/approval cost (§3.3), review surface, one-VPN conflict, and the fact it still cannot express per-instance policy. **[design rule]**

### 3.4 `ptrace` / `task_for_pid` / `dlopen`

Process *inspection* on iOS is answered in §3.2 (no procfs, `ptrace` gated on the target being debuggable, `task_for_pid` behind the same gate). What belongs here is the trio that decides whether RetroBug can build a sandbox at all: **code loading, process creation, and executable memory.**

**`dlopen`: only your own bundle, and that is a net win for isolation.**

* iOS apps may `dlopen` dynamic libraries/frameworks **embedded and signed inside their own bundle**, and may not load code from any other path; loading a foreign or unsigned Mach-O fails at the code-signing level ("code signature invalid"), and App Store Review **2.5.2** requires apps to be "self-contained in their bundles" and forbids downloading, installing or executing code ([doc 04 §2.2](04-ios-feasibility.md), with the Apple signing rule of [doc 04 §1.1](04-ios-feasibility.md): executable pages must carry a valid code signature).
* Therefore **RetroBug-iOS ships all native code — core, IR VM, decoders, every backend — statically linked in the one app binary**, and every guest artifact (`libc.so`, `libGLESv2_cm.so`, `libandroid.so`, `lib/armeabi-v7a/*.so`, `classes.dex`) is **data parsed by RetroBug's own guest ELF loader**, never handed to `dlopen` ([doc 04 §2.2, consequences 1–3](04-ios-feasibility.md)).
* **Isolation reading [inference, from the two rules above]:** this is the one place where iOS's restrictions *strengthen* the sandbox. On Android, guest-native code can in principle be reached by host execution machinery — `apk_data_file` is exempted from the `/data`-exec neverallow, and appdomain is granted `execute_no_trans` + `map` on it (§2.1, §2.2) — so Android RetroBug must actively deny the guest any route by which its `.so` becomes host-executed code, and must keep the §2.2 `execmem` permission from being reachable with guest-controlled bytes. On iOS that route does not exist: no page the guest can influence can ever become executable (see the W^X bullet below), so the guest's escape surface collapses to **exactly** the syscall + shim surface that §1.2 enumerates. Fewer classes of hole to test, but every remaining hole is RetroBug's own.
* Practical corollary for the resolver: because there is no legitimate host `dlopen` of a guest path, **any** code-loading-shaped shim in the iOS build is a bug by definition; CI can assert the linked image contains no `dlopen` call site outside the bootstrap (§Verification test plan, T-27).

**No `fork`, no `execve`, no `posix_spawn` — process-per-instance is off the table.** iOS apps cannot create processes: `fork()` "is no-no", per Apple's own forum guidance, and the community restatement "iOS… we can't spawn new processes" is what makes sideloaded-JIT tooling attach to an *existing* process rather than create one ([doc 04 §5.4](04-ios-feasibility.md), citing [Apple developer forums](https://developer.apple.com/forums/thread/747499) and Saagar Jha). Consequences, in order of how much they hurt:

1. §2.1's primitive — "each bind gets its own process with its own UID" — has **no iOS analogue**; the "one OS process per isolated environment" design in §Recommended Android design is simply not portable. Guest processes must be modelled as **extra threads with separate guest page tables and a private guest PID namespace**, with guest memory protection tracked in software, never by host `mprotect` ([doc 04 §5.4](04-ios-feasibility.md), and its "Core design requirements" bullet on software page protection).
2. **The §1.1 "kernel backstop" requirement cannot be met.** Android's mitigation for a monitor bug is a real seccomp-bpf filter in a process containing no trusted RetroBug code (§2.6). iOS offers neither half: there is no filter API an app can install (no seccomp, and no third-party-callable Seatbelt entry point — Apple documents App Sandbox as a *macOS* facility configured by entitlements: "App Sandbox provides protection… in macOS apps", "To distribute a **macOS** app through the Mac App Store, you must enable the App Sandbox capability" ([App Sandbox](https://developer.apple.com/documentation/security/app-sandbox)); the I/O Kit/`libsandbox` `sandbox_init`-style API is not documented for iOS at all **[UNVERIFIED — T-29 attempts to link and call any sandbox-application symbol on a device]**), and RetroBug cannot put untrusted guest code in a *second* process anyway. **On iOS, therefore, complete mediation is a pure software property of one process. This is the single most important sentence in §3.** **[inference from (1) + the absence of any documented app-facing filter]**
3. The good news, small: with no `execve`, §1.3's "inherited open fds (ambient authority)" row loses its main delivery vehicle, and the `O_CLOEXEC` race it cites cannot occur. FD hygiene (`FD_BASE` offset, capability table) is still required, because fds leak through *shims* and through `dup`/`fcntl(F_DUPFD)`, not through exec.
4. The exact failure mode (`ENOSYS` vs `EPERM` vs sandbox-violation kill) of `fork`/`posix_spawn`/`vfork`/`system()`/`NSTask` on a shipping iOS build is **not documented by Apple**; RetroBug's guest ABI must return a synthesised `EAGAIN`/`ENOSYS` for `fork` and never call the host one. **T-28** records the real behaviour on iOS 26 devices for the leak-probe fixture.

**`mmap` W^X: no RWX, and `MAP_JIT` is not obtainable — full treatment in [doc 04 §1](04-ios-feasibility.md); do not re-derive.** The facts that constrain *isolation* here, quoted there: Apple's `mmap(2)` says that without `MAP_JIT` a `PROT_WRITE|PROT_EXEC` mapping "**A writable, but not executable mapping is returned on iOS, watchOS and tvOS**" (silent downgrade, not error), XNU refuses `MAP_JIT` unless the code-signing monitor blesses it (`vm_map_csm_allow_jit` → `EPERM`), `com.apple.security.cs.allow-jit` is documented **macOS-only**, and Apple states "`pthread_jit_write_protect_np()` **isn't available on iOS**". For §1.2's `mmap` row this yields a clean, testable rule set for the iOS build:

* `mmap` with `PROT_EXEC` **and** a guest-influenced page must be refused by the monitor *before* asking the kernel — not because the kernel would allow it (it will not), but because iOS's silent RW downgrade means a permissive check appears to "work" in the simulator and then faults on first fetch on a device. Assert on-device, not in simulation (**T-30**).
* `MAP_SHARED` (the §1.3 escape row) is still live on iOS: `MAP_SHARED` file-backed mappings into the container are allowed and let writes land in the host file behind RetroBug's back. So the §1.5 item 4 invariant (`allowed_mmap_flags` + `(st_dev, st_ino)` re-verification) is *unchanged* on iOS, and is one of the few FS guarantees here that has no OS assist.
* `shm_open`/POSIX shared memory and `mach_make_memory_entry` are Darwin cross-process surfaces; within RetroBug's single process they are trivially usable by guest code if the monitor exposes them, and they are also the mechanism a *sibling app* could use if Apple's MAC did not cover them (**T-20**, **T-31**). Deny by default in the guest ABI, exactly as §1.2's IPC row prescribes.
* Because there is no executable memory, the iOS code cache is **data** (IR) — which additionally means §2.2's "translated-code cache must not be executed from `/data`" problem, and the whole "is the cache cross-instance aliased?" attack, becomes "is the *IR* interpreted with the wrong instance's register/file mapping?" The attack is still real, and it is still purely RetroBug's (§Verification test plan, T-32).

**Verdict.** On iOS the guest cannot load code, cannot spawn a process, and cannot get executable memory — so its reachable attack surface is narrower than on Android's normal path. But the same three facts remove every OS-level enforcement point RetroBug could otherwise lean on: **no isolated UID, no seccomp, no per-instance process, no obtainable network filter.** The iOS build must therefore treat §1.5's VFS + capability table + §2.8 config store as the *entire* security boundary, hold them to code-review-and-test standard as such, and say so out loud (§3.5).

### 3.5 What must be documented as unachievable on iOS

The project brief requires that any isolation guarantee which cannot be fully achieved on a platform be **documented rather than assumed**. This section is that document, in the form RetroBug must reproduce in product copy. The rule I applied: an item goes on this list if, on Android, it rests on an OS object (§2) and on iOS it does not.

| # | Commitment | Android (§2) | iOS status | What the disclosure must say |
|---|---|---|---|---|
| D-1 | **Per-instance identity the kernel recognises** (distinct UID / SELinux domain per environment) | Achieved: fresh UID from the isolated pool per bind, `isolated_app` domain (§2.1) | **Unachievable.** One container, one UID shared with every app on the device, one Seatbelt profile (§3.1, §3.2) | "On iOS, isolated environments are separated by RetroBug's own software, not by iOS. iOS has no per-profile identity." |
| D-2 | **Separate OS process per environment** | Achieved (`startProcessLocked` → new isolated process each bind, §2.1) | **Unachievable.** No `fork`/`execve`/`posix_spawn`, no launchable app-extension slot, no XPC peer (§3.2, §3.4) | "On iOS all environments run inside the RetroBug process. A defect that corrupts RetroBug's state can affect every running environment, and a crash ends all of them at once." |
| D-3 | **Kernel-enforced filesystem naming denial** (guest cannot name a host file at all) | Achieved in an isolated process: `neverallow isolated_app_all app_data_file_type:file open`, no `dir` perms (§2.1) | **Software-only.** Seatbelt confines RetroBug *as a whole* to its container, so host `open()` of a sibling instance's subtree succeeds at OS level; only the §1.5 resolver refuses (§3.1) | "Isolation between instances relies on RetroBug's own file brokering. There is no second, independent enforcement layer on iOS." |
| D-4 | **Kernel backstop for a monitor bug** (seccomp-bpf `SIGSYS`) | Achievable in the sandbox process (§2.6) | **Unachievable.** No app-installable syscall filter; no app-facing Seatbelt API (§3.4, item 2) | "A software defect in RetroBug's syscall monitor on iOS may allow a guest app to reach iOS APIs. We fuzz and test (§Verification test plan), but cannot bound the failure with the OS." |
| D-5 | **Hard network kill-switch** (`neverallow … socket … create`, §2.1) | Achieved in an isolated process | **Software-only + shim closure.** Monitor denial + closed shim list; Network Extensions are device-global, consent-gated, capability-gated and not per-instance (§3.3) | "Network is disabled by RetroBug's own policy layer. On iOS this is not an OS-enforced prohibition. Optionally, use iOS's own controls (airplane mode, VPN, per-app Wi-Fi restriction) for OS-level cutoff." |
| D-6 | **DNS cannot leak** (§2.7(e): three routes) | Two of three closed by policy in an isolated process, one (AF_UNIX→`dnsproxyd`) still open, T-08 | **Different shape, same verdict:** no `/dev/socket/dnsproxyd`, but resolution goes through `mDNSResponder`/`DNSService*` host calls that a shim can reach without a syscall RetroBug mediates; Apple documents that a provider sees DNS flows *only* for low-level resolver APIs (§3.3) | "DNS lookups are made by RetroBug's host code when a shim asks for them; the OFF state must therefore cover host resolver calls, not just guest sockets." |
| D-7 | **Property / settings surfaces are virtualised** (`/dev/__properties__`, `Settings.*`, §2.8, §1.5 item 6) | Android has these surfaces; RetroBug virtualises them | **Not applicable on iOS, but the analogue exists:** `NSUserDefaults`/keychain are container-global and shared with the main app process by default → the same "no global fallback" rule must be implemented as a namespaced store, never as ambient `UserDefaults` (§2.8, §3.1) | "Guest settings are stored per environment inside that environment's own storage; RetroBug never reads or writes the device-level or app-level default store on a guest's behalf." |
| D-8 | **Teardown actually happens** (exit → drain table → erase root, §1.5 item 7) | Process death is observable; host can clean up | **Cannot be guaranteed at the moment of kill.** Suspension/jetsam may stop all code without an orderly exit (TN2277, [doc 04 §5.4](04-ios-feasibility.md)) | "If iOS terminates RetroBug abruptly, an environment's files may persist until the next launch reaps them. Sensitive environments should be created with **encrypted-at-rest + crypto-erase** semantics (below)." |
| D-9 | **The environment is not the default** | Product rule | **Same on iOS**, but note the opposite failure mode: on iOS the isolated environment is *less* protective than users will assume, so "advanced/optional" framing must be explicit rather than implied | "Isolated environments are optional and clearly marked; on iOS they provide profile separation, not an OS sandbox." |
| D-10 | **Executable memory / JIT parity** | `execmem` permitted (§2.2) | **Unachievable and unrelated to isolation** — but it *does* change the attack surface (guest cannot execute host code, §3.4) | "The iOS build runs the guest without a JIT; guest native code is interpreted, so guest code can never execute as host machine code." |

**Mitigations that partially restore D-3/D-8 on iOS (use them, and say they are partial).**

1. **Crypto-erase instead of delete.** Give every isolated environment its own per-instance data key held in the iOS Keychain (`kSecClassGenericPassword`, non-sync, `kSecAttrAccessibleAfterFirstUnlock`/`WhenPasscodeSetThisDeviceOnly`), wrap the instance root's contents with it, and set Apple's strongest available file protection on the files — `FileProtectionType.complete`: "The file is stored in an encrypted format on disk and cannot be read from or written to while the device is locked or booting" ([Foundation `FileProtectionType`](https://developer.apple.com/documentation/foundation/fileprotectiontype), iOS 2.0+; `.completeUntilFirstUserAuthentication` and `.completeUnlessOpen` are the weaker variants, `.none` exists and must be rejected by a unit test). Then destroying the *key* at teardown makes the residue unreadable even when code never got to run (D-8), which is the closest iOS gets to "teardown erases the environment". **[design rule]**
2. **Self-check on entry, not on exit.** Because abrupt death is expected, the resolver must re-verify on entry that no *other* instance's root is open in the process's fd table and that the instance's expected `(st_dev, st_ino)` pair matches (§1.5 items 1–2), so a stale/aliased state after a jetsam kill fails closed rather than serving one instance's files to another.
3. **Defence in depth without an OS:** the same §1.5 resolver should be implemented twice — once in the production path and once as an independent *checker* (a second, simpler re-implementation run in CI on every logged `(path, flags) → decision` trace, disagreeing loudly). Different code, same verdicts, is the only substitute available on iOS for "the kernel disagrees with the bug". **[inference: a differential oracle compensates for the missing backstop; it is not equivalent and D-4 stays on the list.]**

**Ship-blocking rule [design rule].** RetroBug-iOS must not reuse RetroBug-Android's isolation copy anywhere. Every string — the entry sheet, the settings row, the App Store description, the landing page, the FAQ — goes through a per-platform wording table, and the disclosure list D-1…D-10 must be published in-app (Settings → About isolated environments) with the research date and the platform. If a future iOS release adds a relevant primitive (e.g. a documented "background execution/daemon extension" for third parties, or an obtainable per-instance process), the entry moves from this table to §2's list **only with a citation and a passing device test.**

**Strength ordering, and the design rule that follows.** kernel/MAC-without-consent (`isolated_app`, neverallows) **>** kernel/MAC-with-user-consent (`VpnService`, NE providers) **>** self-installed kernel filter (seccomp, negative-only) **>** software mediation (monitor + VFS + namespaced store) **>** convention (docs, code review, "we don't call that API"). Every product commitment must be anchored as high on that list as the platform allows, and **anything anchored below "self-installed kernel filter" must be covered by a passing test, not by prose.** On Android all six commitments reach the top two tiers (network, FS naming, service discovery, UID identity) with two software-tier items (config namespacing, per-instance policy granularity). On iOS **four of six** sit in the software tier by necessity (§3.5 D-1…D-5), which is why the test plan is a release gate rather than a nicety.

## Recommended Android isolated-environment design

**The decision, in one paragraph.** One isolated environment = **one bound `android:isolatedProcess="true"` service**, freshly spawned per bind, so it gets its **own UID from the isolated pool** and the `isolated_app` SELinux domain (§2.1). The **host (main) process is the resolver, fd broker, system-service proxy and the only place with GPU/audio access**; the sandbox process runs the vCPU, the guest RAM, the JIT arena and the guest-visible fd table; every path-bearing syscall is an RPC to the host, and every policy decision is authenticated by **`Binder.getCallingUid()`, which the kernel — not RetroBug — stamped onto the connection**. That UID *is* the instance token: no other primitive on either platform lets RetroBug prove *which* environment is asking, which is why `:slotN` (§2.3) is disqualified and this one is not.

### Topology

```
 RetroBug host process (app UID, untrusted_app)
   UI · lifecycle · profile store (§2.8)
   InstanceResolver (§1.5) ── instance_root_fd, host-fd capability table
   FdBroker ──bind──► ParcelFileDescriptor ──► sandbox
   ServiceProxy: guest Activity/Clipboard/Audio/Sensor ⇒ host-side impls (§2.1: 3 findable services only)
   GraphicsHost + AudioHost: GLES command replay, AAudio/OpenSL sink (§doc 03)
   PolicyCache: {networkOn, instanceId} per sandbox
        │  bindService(isolated service) → new process, new UID, isolated_app domain
        ▼
 Isolated process (AID 99000+ / 90000+, isolated_app)
   vCPU threads (TSYNC'd seccomp filter, §2.6) + IR/JIT arena (self:process execmem, §2.2)
   guest RAM arenas (anonymous mmap / own memfd ⇒ appdomain_tmpfs, §2.2 item 6)
   guest fd table (guest fd = host fd − FD_BASE), §1.5 item 4 — instance-local by construction
   syscall monitor: decide here, ask host to act
   NO gpu_device, NO non-AF_UNIX socket creation, NO app_data_file open  ← all neverallow-enforced
```

**Why the resolver must be in the host, not the sandbox.** `neverallow isolated_app_all app_data_file_type:file open` plus the absence of any `dir` permission in `private/isolated_app_all.te` (§2.1) means the sandbox physically cannot do path resolution against instance storage; and it *should not* have to, because that is precisely the property RetroBug wants to sell. The consequence to accept explicitly: **the host process is the Trusted Computing Base of the isolated environment** — a resolver bug in the host can yield an out-of-instance *fd*, but cannot yield network, GPU, service discovery, or the ability to name a file from the sandbox side. State it in the threat model: "sandbox bug ⇒ bounded by SELinux; host-resolver bug ⇒ bounded by the fds it hands out (T-02, T-35)."

### The service contract

```xml
<service android:name=".iso.IsoGuestService"
         android:isolatedProcess="true"
         android:exported="false"
         android:process=":iso" />   <!-- ignored for isolated services; keep explicit for clarity -->
```
* Bind with `BIND_AUTO_CREATE` only while the environment is *entered*; `unbind()` on exit. One bind = one environment; **never** reuse a process across environments (§2.1: the framework already can't).
* Do **not** set `useAppZygote` in v1. The app zygote is the right end-state (pre-warm translator tables and guest `.so` parses once, fork per instance — §2.2's last bullet), but it adds a permanently resident process and makes memory behaviour "depend on how many isolated services share it". Measure first; the `:iso` cold-start cost is the translator's table build, which is data (§Recommended iOS design shares it).
* `exported="false"` + a signature-scoped `IBinder` interface; the AIDL surface must contain **no** method that accepts a host path, and **no** method that accepts an instance id (it is derived from the calling UID). **[design rule]**

### Where the instance root lives, and how it is brokered in

1. Root: `/data/data/<retrobug>/files/retrobug/profiles/<appId>/<instanceId>/root/`, `0700`, created and opened **only** by the host. Host keeps `instance_root_fd` (`O_PATH|O_DIRECTORY|O_CLOEXEC`) and verifies the stored `(st_dev, st_ino)` at `CREATE`, at every `ENTER`, and re-checks on `mmap(MAP_SHARED)`/`link*`/`rename*` (§1.5 items 1–4).
2. **The guest APK is copied into the instance** at `…/root/.retrobug/package.apk` and never referenced as `/data/app/…/base.apk`. Reason, from §2.1: `apk_data_file` is *not* `app_data_file_type`, and appdomain (hence `isolated_app`) is granted `apk_data_file:dir {open getattr read search …}` and `apk_data_file:file {getattr open read ioctl lock map x_file_perms}` — so an isolated process can, by path, **read and list other apps' installed APKs** [inference from the quoted grants; **T-34** verifies, and also checks whether `getattr` on an arbitrary `/data/app/<pkg>` path is a package-presence oracle]. The in-instance copy is opened by the host and passed as an fd, which the sandbox may `read`/`map` (the received-fd allow) but — note — **not** `execute`: `execute` is absent from `{ append read write getattr lock map }`, which conveniently matches the design (guest code is *parsed*, never executed natively; §3.4's iOS-parity argument).
3. Shared rings (pixels, samples, guest log) are **host-created files inside that instance's root**, `ftruncate`d, `MAP_SHARED`, fd passed over Binder. This is the sanctioned channel: exactly "Access already open app data files received over Binder or local socket IPC" (§2.1), instance-scoped by construction, and closed by teardown. A `memfd`/`tmpfs` ring created by the *host* and passed *into* `isolated_app` is **not** covered by the quoted allow → **T-33** tests it; if it fails, the file-in-root route is the design, not the fallback.
4. Guest RAM and the translated-code arena are **sandbox-owned** anonymous `mmap`s / sandbox-created memfds (`appdomain_tmpfs` executable for that domain, §2.2 item 6) — never shared with the host, so the host's bug cannot touch guest RAM and the guest's writes cannot escape the process.
5. `/system`, `/proc`, `/sys`, `/dev` are `virtual` backends served by the monitor (§1.5 item 3, 6); **there is no writable shared mount anywhere** — no `obb`, no `android_data_file` outside the root, no `/data/local/tmp` (also `dontaudit isolated_app_all shell_data_file:dir search`, §2.1).

### Graphics and audio stay host-side

Because `neverallow { isolated_app_all -isolated_compute_app } gpu_device:chr_file { rw_file_perms execute }` (§2.1), the sandbox has no driver. So: guest `eglSwapBuffers`/`glDraw*` → RetroBug's command stream into the instance-root ring → **host** replays on the real GLES/Vulkan backend (doc 03 §3, §6) → the composed framebuffer is returned (or, at the lowest fidelity tier, the host renders the guest's software framebuffer and only pixels cross). Audio: guest `AudioTrack`/OpenSL ES buffers into the ring → host `AAudio`/`AudioTrack` sink; `AudioRecord` input likewise flows host→sandbox through the ring. Binder-carried `native_handle`/dmabuf fds are **not** the mechanism: the inbound-fd allowlist is deliberately tiny (§1.3 "Binder" row) and a dmabuf heap node is a `chr_file` this domain has no claim on **[inference; T-36 confirms `AHardwareBuffer` fd usage from `isolated_app` — if it works it is the fast path, and it stays off by default].** Cost is one copy per frame plus an extra IPC hop; mitigation is a bounded-depth ring + drop-policy on the guest side, which the software-framebuffer tier already needs.

### Self-installed seccomp filter (the backstop)

On the first line of the sandbox process, before any guest state exists: `prctl(PR_SET_NO_NEW_PRIVS, 1)` (T-06), then `seccomp(SECCOMP_SET_MODE_FILTER, SECCOMP_FILTER_FLAG_TSYNC, &prog)` with `SECCOMP_RET_KILL_PROCESS` default and explicit `ERRNO(EACCES)` for: `execve`, `execveat`, `ptrace`, `process_vm_readv/writev`, `pidfd_open`, `pidfd_getfd`, `kcmp`, `unshare`, `setns`, `socket` where `domain ∉ {AF_UNIX}` (and `AF_UNIX` `connect` is brokered by the monitor anyway), `connect`, `bind`, `sendto`, `sendmsg`, `sendmmsg`, `bpf`, `perf_event_open`, `userfaultfd`, `mount`-family extras, `ioctl` on any fd not in RetroBug's own small set (see §2.6's caveat that BPF cannot discriminate ioctl by identity, so ioctls are brokered, not filtered). Everything the Android app baseline already removes (`openat2`, `io_uring_*`, `landlock_*`, `pivot_root`, `keyctl`) stays removed; RetroBug's filter can only narrow (§2.6). **Filter the whole thread group with TSYNC** — a per-thread filter leaves a hole through the guest's own worker threads.

### Lifecycle and state machine

```
          create()                 enter(userGesture)              run
 NONE ────────────► CREATED ────────────────────► ENTERING ─────────► RUNNING
   ▲                  │  profile dir + record       │ bind→ new UID+       │
   │                  │  config row, key material   │ root-fd verify       │ guest executes
   │                  │  NO process                   │ first fds handed    │
   │                  ▼                              ▼                      ▼
   │              ABANDONED ◄──── teardown ──── EXITING ◄── exit()/user ────┤
   │                              (drain tables, assert empty, unbind)      │
   └───────────────────────────  TEARDOWN_DONE ◄────────────────────────────┘
                                              ▲
        REAPED (SUBREASON_ISOLATED_NOT_NEEDED, │ abnormal: kill, crash, OOM
        bind refused, uid pool exhausted) ──────┘ → durable state is on disk,
                                                  next ENTER rebuilds or fails loudly
```
* **CREATE** — host only: mkdir roots `0700`, write the profile record and the config row (`ProfileStore(instanceId)`, §2.8), record `(st_dev,st_ino)` of the root. No process, no network decision change, no user-visible "running" affordance.
* **ENTER** — requires an explicit user gesture (never the default, per the Scope reminder at the top of this document): bind → the framework starts a fresh isolated process → host verifies the new caller UID maps 1:1 to this `instanceId` → re-verify root identity → hand the APK fd, the ring fds, the policy object (`networkOn`, resolved from the instance's own config row), and the synthetic `/proc` table. **If any step fails, ENTER fails visibly.** There is no path from a failed ENTER into the normal in-process execution — "never a silent fallback" is enforced by code structure: the guest loader lives in the sandbox and cannot be instantiated in-process **[design rule; T-37 asserts this by killing the bind and checking no guest thread exists]**.
* **RUN** — policy is a *pair*: the sandbox refuses (UX + granularity) and the host's shims refuse (soundness), both reading the same cached decision (§2.7(d)).
* **EXIT** — quiesce the vCPU at an instruction boundary, flush guest FS state (`msync`-equivalent per §1.5), stop accepting new RPCs, `unbind()`. The process may then be reaped at the OS's convenience — RetroBug must not depend on it for correctness (§2.1: "killed as soon as they stop being needed", `SUBREASON_ISOLATED_NOT_NEEDED`).
* **TEARDOWN** — assert **both** fd tables empty (§1.5 item 7 — a non-empty table is a leak by definition, T-11), close `instance_root_fd` and every backend fd, drop the mount trie, then delete or archive the root, and mark the profile record torn down. A crash between EXIT and TEARDOWN must be recoverable: teardown is idempotent and re-runs at next launch from the profile record.

### Config binding to that app's profile, with no global fallback

`ProfileStore(instanceId)` keyed by a mandatory `instanceId`, `NamespacedKey{instanceId, domain, name}`, no API accepting an un-namespaced key (§2.8). On Android specifically: **the store's file lives inside the instance root**, so §2.1's FS guarantee *is* the config guarantee; the sandbox reads it only through a brokered fd. The network opt-in flag is one row in that store — it is never mirrored into `SharedPreferences`, `Settings.System/Secure/Global`, or a system property, and guest `Settings.*` reads are answered by the namespaced shim, because those keys are per-*package* in a global table and RetroBug has one package (§2.8 last bullet). Defaults come from a compiled `(guestPackage, configName)` table, so "no profile → lookup fails" is unit-testable (T-38).

**What this design deliberately does *not* use:** `:slotN` as an isolation boundary (§2.3 — same UID), user/mount namespaces (§2.4–2.5), `openat2`/Landlock (§1.4), `VpnService` as the per-instance kill-switch (§2.7(a)), App-Ops-style background restrictions (§2.7(c)), and any `app_process`/`ndk_translation`-style privileged helper (out of reach for an unprivileged app; `app_zygote` is the only zygote RetroBug may ask for, via `useAppZygote`).

## Recommended iOS design + honest limits

**The decision, in one paragraph.** On iOS an isolated environment is **an `InstanceContext` inside the single RetroBug process**, owning everything that can be owned per instance: its own root dirfd (opened from inside the app container, identity-pinned), its own guest-fd capability table, its own mount trie, its own synthetic `/proc`, its own `Policy` object (`networkOn`, resolved from that instance's config row), its own IR/code-cache arenas tagged with `instanceId`, its own guest-PID namespace, and its own key-wrapped storage. The **resolver, the policy check and the table validation are the same code as Android's §1.5 design** — one implementation, two platforms — but on iOS it is the *only* implementation, so it additionally gets an independent re-implementation used as a differential checker over logged decision traces (§3.5 mitigation 3). There is no second process, no second UID, and no kernel filter; RetroBug refuses, and the test suite must be able to show that it refused.

### Topology

```
 RetroBug-iOS process (app container, uid mobile, one Seatbelt profile)
   UI (UIKit/Metal presentation)
   InstanceContext[instanceId]                    ← the whole isolation boundary
       root_fd + mount trie + resolver (§1.5)      ← SHARED CODE with Android, no #if
       guest fd table (per-instance FD_BASE)
       synthetic /proc, /sys, /dev
       Policy { networkOn, hostResolversOn }       ← read-only copy of the instance's config row
       IR arenas + per-instance code-cache key (§2.9 last row)
       guest PID/UID namespace (software), guest clock offsets
       GL/Metal object-handle namespace (guest name ⇒ host name, per instance)
   Closed shim layer: the ONLY place that may call Foundation/Network/CFNetwork/Multipeer
   Snapshot manager: save-state on didEnterBackground (doc 04 §5.4)
   Key service: per-instance data key in the Keychain (non-sync), FileProtectionType.complete on files
```
Guest "processes" are **threads with software page tables** ([doc 04 §5.4](04-ios-feasibility.md)) — never host processes, which do not exist for us (§3.4).

### Where the instance root lives

`Library/Application Support/RetroBug/profiles/<appId>/<instanceId>/root/` inside the data container — **not** `Documents/` (iCloud/iTunes backup, user-visible via Files), **not** `tmp/` or `Library/Caches/` (system may purge while suspended), per §3.1's quoted backup/purge table. Every file: `FileProtectionType.complete`, and the content wrapped by the instance's Keychain-held key. Imported APKs land in a `staging/` path exposed to the resolver as `ro-shared` only, and are copied into the instance before execution; **no App Group is used for instance data** (§3.1), and the import hand-off (Share Sheet / Files) is the only sanctioned exception, with the rule that anything arriving via a group container is untrusted input, never a mount.

### Graphics, audio, input

Everything is in-process, so there is no transport to design — which is precisely the risk: it is tempting to let guest code touch host objects directly, and that would break isolation *inside* the process. Two invariants, testable:
1. **Guest GL/Metal handles are per-instance integers.** A guest `glGenTextures` name maps through `InstanceContext.glHandles`, so instance B's integer can never resolve to instance A's `id<MTLTexture>`/`GLuint` (**T-40**). Shared host state that has no per-instance mapping (a global `EAGLContext`, `AVAudioEngine`, a singleton formatter) is a bug, not a shortcut.
2. **No host object identity crosses into guest memory.** Guest-visible buffers are copies or guest-side regions; a `NSData`/`CMBlockBuffer` pointer must never be written into guest address space, because guest-controlled pointers in a single address space are an escape, not a fast path **[design rule]**.
Rendering backend: Metal (optionally MoltenVK) behind the same command-stream abstraction as Android (doc 03 §3 and §6); audio through `AURenderCallback`/`AVAudioEngine` with the real-time rules from [doc 04 §5.2](04-ios-feasibility.md).

### Network

Monitor refusal for every guest socket-family syscall (`AF_INET`/`INET6`/`LINK`/`VSOCK`/`SYSTEM`/`PF_ROUTE`), `EACCES` when OFF, plus **the closed shim list enforced by linkage, not review**: the guest-facing code path may not link `URLSession`/`CFNetwork`/Network.framework/`DNSService*`/Bonjour/GameKit/CloudKit/WebKit (§3.3's verdict list); CI asserts it by scanning the linked symbols of the guest-facing object files (**T-27**) and a device test asserts zero egress with `networkOn=false` while a probe guest tries every route (**T-14**..**T-17**). DNS is answered from the instance's own hosts table; if `networkOn=false`, resolution is refused **before** any host call, because on iOS the resolver is a host service reached without a guest-visible syscall (§3.3, D-6).

### Lifecycle

`CREATE` (root + key + config row; no threads) → `ENTER` (explicit user gesture; verify root `(st_dev,st_ino)`; assert no other instance's fds in the process; start vCPU threads; deliver a per-instance "you are in an isolated environment" banner that stays on screen — the iOS substitute for Android's system-enforced separation, so that the user can tell which mode they are in) → `RUN` → `PAUSE` (on `applicationWillResignActive`/`didEnterBackground`: quiesce at an instruction boundary, snapshot, because suspension stops all code — TN2277/[doc 04 §5.4](04-ios-feasibility.md)) → `EXIT` (stop RPCs, drain guest FS, destroy the instance's IR arenas and glHandles maps) → `TEARDOWN` (**destroy the Keychain key first**, then unlink the tree; a non-empty fd table here is a leak by definition, **T-11**) — plus `REAPED`: jetsam/teardown-interrupted leaves an orphan tree, which is reaped at next launch from the profile journal, and whose contents are already unreadable because the key is gone (or, if the key survived, are `FileProtectionType.complete`).

### Config binding, no global fallback

Same `ProfileStore(instanceId)` closed-lookup design (§2.8), file inside the instance root. On iOS the ambient-defaults hazard is sharper than on Android because `UserDefaults.standard` is one process-global object: the guest-visible settings shim **must not** touch `UserDefaults`, `NSUbiquitousKeyValueStore`, or the default keychain access group; guest `Settings.System` equivalents are answered from the instance store (**T-38**, **T-41**). Host (RetroBug's own) preferences live in a different store that the guest cannot address, per §2.8 item 3.

### Honest limits — the wording RetroBug must use on iOS

* **Not OS-enforced between instances.** "iOS gives RetroBug one sandbox. Inside it, separated environments are separated by RetroBug's own code; iOS does not provide a second, independent enforcement layer for them." (§3.1, §3.2, D-1…D-4)
* **Shared process, shared blast radius.** "All environments run in one process. A crash — or iOS reclaiming memory — affects all of them; a software defect in RetroBug could let one environment reach another's files or memory." (D-2)
* **No kernel backstop.** "Android can make the kernel refuse a guest's request; iOS cannot, so on iOS these refusals are software and are validated by our test suite." (D-4)
* **Network OFF is a policy refusal.** "Turning network off means RetroBug refuses the guest's network calls and refuses its own network code on the guest's behalf; it is not an iOS-level firewall. For an OS-level cutoff use Airplane Mode / your own VPN / Screen Time web restrictions." (D-5)
* **Teardown may be interrupted.** "If iOS ends RetroBug abruptly, an environment's files may persist until the next launch; they are encrypted with a per-environment key and marked complete protection, so they are unreadable while the device is locked, and deleting the environment destroys the key." (D-8)
* **What *is* genuinely true on iOS:** other apps cannot read any of it (§3.1); guest code can never execute as host machine code, load code, or spawn a process (§3.4); no shared mount, cache or scratch is required by the design (§3.1 item 1); isolated settings are written only into that environment's own store and are never global (§2.8); the environment is never the default and entry is always a deliberate, visible action (product rule, §3.5 D-9).

**Migration rule [design rule].** The iOS and Android builds share the resolver, the capability table, the mount trie, the policy object and the profile store **byte-for-byte** (one C++ core, per [doc 04](04-ios-feasibility.md)'s "two products, one core"). Platform-specific code may only supply *backends* (fd brokering vs direct open; seccomp install vs nothing; Binder vs in-process call). If a platform branch appears inside `resolve()`, isolation on the other platform is now untested by construction.

## Verification test plan

**Why this suite exists.** Per §2.9's honest summary, most of RetroBug's promises are "RetroBug enforcing rules on itself". Those are the only promises in the project that can be *falsified cheaply*, so they are tested as attacks, not as unit tests. Rules:

1. Every test is an **adversarial action attempted from inside an isolated environment**, with a stated **expected failure**, an **automation hook**, and a **platform**. "Crashed" is never a pass — the expected result is a specific `errno`, or a refusal the host itself can prove (`SECCOMP_RET_ERRNO`, `SIGSYS`, absent fd, absent log line).
2. **Oracle discipline** (§1.2): refusals must be indistinguishable between "absent" and "forbidden". Tests therefore assert both the *outcome* and the *shape* of the outcome (`ENOENT`, not `EACCES`/`ENOTDIR`/`EPERM` where §1.2 requires one errno).
3. Every test runs in **three modes**: `NORMAL` (in-process path), `ISO-ANDROID` (isolated service, §Recommended Android design), `ISO-IOS` (single-process `InstanceContext`). A difference in *outcome* between the two ISO modes is a bug in the shared core (Migration rule); a difference in *severity* is expected and belongs in §3.5's wording.
4. **Golden traces.** The monitor logs every `(instanceId, syscall, path, flags) → decision`; the differential checker (§3.5 mitigation 3) replays the log through an independent resolver implementation and fails on disagreement. This is the iOS substitute for a kernel backstop, so it is release-gating.

### The leak-probe guest APK (test fixture)

A real `armeabi-v7a` APK, committed as source + a hash-pinned prebuilt, that RetroBug loads like any guest:

* **Build.** NDK with `APP_ABI := armeabi-v7a` / `abiFilters "armeabi-v7a"`, `-march=armv7-a -mfloat-abi=softfp -mfpu=neon`, `APP_PLATFORM` pinned to a 32-bit-era level so the binary stays in the class RetroBug targets. No `asm` requiring armv8. Link **statically** (`-static-libgcc`, no external `.so` dependencies beyond what RetroBug claims to implement) so the guest's libc surface is exactly RetroBug's shim set — that is the point.
* **Two attack paths.** (1) *Shim path:* call guest `open`/`stat`/`opendir`/`socket`/`getaddrinfo`/`mmap`/`syscall()` — this exercises what a normal legacy app does. (2) **Raw path:** inline `svc #0` with explicit ARM EABI numbers from §1.2's table (`openat2` 437, `ptrace` 26, `pidfd_getfd` 438, `unshare` 337, `socket` domain args, `mknodat` 324, `linkat` 330 + `AT_EMPTY_PATH`, `sendmsg` with a hand-built `msg_control`, `io_uring_setup` 425, `keyctl`) — this is what proves the *guest ABI* is closed, independent of RetroBug's own libc wrappers. A "sweep" mode iterates nr 0..500 with harmless args, logging the disposition of each; the diff against the golden sweep catches a newly-forwarded syscall the moment it appears.
* **Output.** One JSON line per probe: `{probe, arg, ret, errno, ts, instanceId}` plus a final line summarising `readlink("/proc/self/fd")`, `getcwd`, `statfs` ids, and the guest's own view of its fd table. Host side appends `decision_source ∈ {sandbox-monitor, host-resolver, seccomp, selinux, ok}` so a refusal is attributable — a test that passes because SELinux saved us must be labelled as such (§Recommended Android design's TCB statement).
* **Pairing.** The fixture ships as **two** guest APKs (`ProbeA`, `ProbeB`) so every cross-instance test is genuinely two-environment, and each writes a canary file containing its own instance token; reading the other's canary is the pass/fail signal.
* **Negative control.** A `SafeApp` guest that touches nothing forbidden; if any of its calls are refused, the suite is broken, not the sandbox.

### CI shape — real devices are not optional

* **Why a lab is required.** The guest is `armeabi-v7a` and Google's maintained emulator images do not provide a 32-bit ARM Android runtime to host it on; more decisively, **most assertions in this suite are about OEM-provided policy** — SELinux `neverallow`s, the generated app seccomp filter (T-13), Yama (T-04), the isolated UID pool (§2.1), property and `/proc` surfaces (T-19), `ApplicationExitInfo` reasons (F-1). An emulator that happens to run the guest would validate none of them.
* **Matrix.** A pinned set of 5–8 physical devices spanning: GKI 5.10 / 6.6, Android 13/14/15/16, at least one OEM build known for extra policies, one low-RAM device (to force reaping, F-1), and one 16 KB-page device ([doc 04](04-ios-feasibility.md) page-size note). iOS: 4 physical devices across the floor version and the current one, **never the simulator** for T-30/T-22/T-23/T-28/T-29 (the simulator has Mac kernel semantics and would pass tests that fail on device).
* **Runner.** Long-lived lab hosts (USB + `adb`) rather than cloud-only, because (a) isolated services need a real foreground client held open for minutes, and (b) several tests must *observe* system behaviour (`dumpsys`, `am`, `ApplicationExitInfo`, `logcat -b events`) and need repeatable device state (reboot between destructive tests: T-05, T-13, T-35). Where a cloud farm is used, prefer physical-device pools; virtual-device pools cannot run the guest ABI tests at all.
* **Denial observability.** On user builds an app cannot read `avc: denied`, so: run the suite on **userdebug/eng** images where `dmesg`/`logcat` show SELinux denials (this is how T-08 and T-34 get attributed to the kernel rather than to RetroBug), and on user builds fall back to RetroBug's own audit log plus `SIGSYS`/`ApplicationExitInfo` signals. State the reduced attribution in the report rather than dropping the test.
* **Gating.** T-01..T-03, T-09..T-12, T-14..T-17, T-19..T-20, T-27, T-32, T-35, T-37..T-42 block release. T-04..T-08, T-13, T-21..T-26, T-28..T-31, T-33..T-34, T-36 are **characterisation** tests: they may not fail the build, but they must not *change disposition* without an updated §3.5/§Recommended-design text — the golden files make a silent policy change visible.
* **Report format.** Per device: uid observed, filter disposition, refusal-by-tier table (kernel/MAC vs self-filter vs software vs absent), plus the raw trace. This is also the artifact the §3.5 disclosures cite.
